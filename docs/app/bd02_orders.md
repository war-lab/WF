# 基本設計 BD02 注文と英文

更新日：2026-10-26

位置づけ：注文と共同注文の表し方、条件の判定、点の計算、注文の生成、宣言の英文の組み立て、乱数を定める。

ルールはルールブック v0.9 の06章と08章を正とする。注文の生成は `sim/ordergen.py` を移植の元とする。

## 結論

注文の条件は5つの形（ちょうど、合計、同数、動物の頭数、ボーナス）で表す。ルールブック08章の印刷用36枚は、すべてこの5つの形で表せる。

点は千分の一点の整数で計算し、半点の整数に丸める。印刷用の注文34枚（ボーナス注文を除く）と共同注文の24行について、この計算式で求めた点が、ルールブックに書かれた点とすべて一致することを確かめた（付録 A）。

宣言の英文は、行動の種類と選んだ物から組み立てる。数は英語の数詞で書き、99まで対応する。模擬の `noun` は8までしか対応しておらず、ボーナス注文で9個以上を出す英文を作れないためである。

移植の元の `sim/ordergen.py` は、動物の頭数の注文に「そのうち1頭はニワトリ」のような指定を付ける。ルールブック v0.9 にはこの指定がない。アプリはルールブックに合わせて指定を付けない形を既定とし、設定 `animalInclude` で切り替えられるようにする（6章 Q1 で確定）。

共同注文の行の産物と数は、通常の注文の条件と同じく読解の対象とし、画面には英文と行の点だけを出す（2.4）。

## 1. 注文の型

```ts
type OrderLevel = "easy" | "medium" | "hard" | "bonus";

interface Order {
  id: OrderId;
  text: string;                 // 注文の英文。公開
  level: OrderLevel;            // 秘密。生成と記録の書き出しにだけ使い、端末には送らない
  isBonus: boolean;             // 公開。紙ではボーナス注文の表の色が違う
  picture: Product | null;      // 「易」の注文に付ける絵。公開
  to: string | null;            // 宣言に使う宛先（例 "the cafe"）。公開
  cond: OrderCondition;         // 秘密。届けると宣言するまで、どの端末にも送らない
  hp: HalfPoints | null;        // 秘密。ボーナス注文は null（出した数で決まる）
  source: { mode: "generated"; seed: string } | { mode: "fixed"; printedNo: number };
}

type OrderCondition =
  | { k: "exact"; items: Bag<Product> }                         // 書かれた数ちょうど
  | { k: "total"; allowed: Crop[]; total: number }              // 合わせてちょうど total
  | { k: "same"; pair: [Product, Product]; min: number }        // 同じ数ずつ、min 以上
  | { k: "animals"; min: number; include: Animal | null }       // 動物 min 頭以上
  | { k: "bonus"; accepted: Product[] };                        // 受け付ける種類

interface JointOrder {
  id: OrderId;
  text: string;                 // 公開
  to: string;                   // 宣言に使う宛先（例 "the village festival"）
  lines: [JointLine, JointLine, JointLine];   // 英文に出てくる順。hp だけ公開し、product と n は秘密
}
interface JointLine { product: Product; n: number; hp: HalfPoints }
```

注文の点 `hp` を秘密にするのは、紙の注文カードで点を条件と同じ折り返しの下に書くためである（ルールブック08章の一覧で、点は条件の隣の列にある）。点が見えると、点から条件を推測できる場合がある。

この扱いは、紙のカードで点を折り返しの下に書く、という解釈による（6章 Q2 で確定）。

難易度 `level` を端末に送らないのは、紙で見分けられるのが、絵のある「易」の注文と、表の色が違うボーナス注文だけだからである。「中」と「難」は紙では見分けられない。「難」と表示すると、半ダース、合計、同数のどれかだという手がかりになる。

不成立になった注文の `cond` と `hp` は、出来事で一度見せたあと、表示用の状態では再び隠す（BD01 8.1、ルールブック06章「開いた折り返しは元に戻す」）。

## 2. 条件の判定

届けると宣言した物を、条件と照らして成立か不成立かを決める。

### 2.1 通常の注文

`deliverOrder(orderId, items)` の `items` は、出す産物の `Bag` である。

| 条件の形 | 成立する条件 |
|---|---|
| `exact` | `items` が `cond.items` と完全に一致する。余分な種類があっても、数が多くても少なくても不成立 |
| `total` | `items` の種類がすべて `allowed` に含まれ、数の合計が `total` に等しい。`allowed` の一方が0個でもよい |
| `same` | `items` の種類が `pair` の2つだけで、2つの数が等しく、それぞれ `min` 以上 |

ルールブック06章の「at least とある注文だけは、多くてもよい」は、`same` の `min` と `animals` の `min` で表す。`exact` と `total` は、数がちょうどでなければ不成立である。

`at least` の注文で多く出した分は戻らない（ルールブック06章）。`same` で成立したときは、出した `items` をすべて受け取る。

成立したら、`items` を手札の産物から引き、`hp` 点と `orderCoins`（2）コインを払う。不成立なら、産物は引かず、sell を山に戻す。

### 2.2 動物の頭数の注文

`claimAnimalOrder(orderId)` は物を出さない。宣言した人の区画にいる動物の頭数（ニワトリと牛の合計）が `min` 以上で、`include` があればその動物が1頭以上いれば成立する。

頭数は自分の区画から自動で数えるため、宣言の英文と実際の頭数が食い違うことはない（方式設計6章）。

不成立になりうるのは、読み違えて宣言した場合（例：2頭で「3頭以上」の注文に宣言した）である。sell を使わないため失う物はないが、その手番は同じ注文に再び宣言できない。

### 2.3 ボーナス注文

`deliverBonus(orderId, product, n)` は、`product` が `accepted` に含まれれば成立する。

成立したら、産物を n 個引き、次の点とコインを払う。

| 産物 | 点（半点） | コイン |
|---|---|---|
| egg | `floor(n / 2)` | n |
| そのほか | `floor(2n / 5)` | n |

半点で表した式は、ルールブック06章の「出した数×0.2（卵は×0.25）を0.5点刻みで切り捨て」と同じ値になる。卵は 0.25n 点＝0.5n 半点、そのほかは 0.2n 点＝0.4n 半点で、切り捨てると上の式になる。

点に上限はない。n は1以上なら受け付ける。

### 2.4 共同注文

共同注文の行の産物と数は、読解の対象である。ルールブック08章は共同注文の印刷用について「行の点は表に出しておいてよい（読み解く対象は、どの産物をいくつ出すか）」としている。そこで、画面には英文と行の点だけを出し、行の産物と数は出さない。行の点は、英文に出てくる順に並べる。

`contributeJoint(jointId, product, n)` は、本人が英文から読み取った産物と数を指定する。空いている行のうち、産物と数がちょうど一致する行があれば、その行として受け付ける。一致する行がなければ `JOINT_MISMATCH` で拒否し、sell も産物も失わない（ルールブック06章「行と合わない数や産物を出したときは受け付けない（カードも産物も戻す）」）。

通常の注文と違い、読み違えても sell を失わず、同じ手番に指定し直せる。ルールブック06章の共同注文の規定が、不成立ではなく「受け付けない」としているためである。

1枚の共同注文の3行は、産物の種類がすべて違う（5.3）。そのため、産物と数から行が1つに決まる。

本書と方式設計の初版は、この08章の記述を逆に読み、「行は読解の対象ではない」としていた。多角レビューで誤りが分かり、改めた。

## 3. 点の計算

### 3.1 通常の注文

ルールブック08章の式を、千分の一点の整数で計算する。

```text
e = 300 + Σ(重み × 数) + 300 × (種類の数 − 1) + (「難」なら 500)
半点 = floor((2e + 500) / 1000)
半点を 1 以上 6 以下に収める（0.5点以上3点以下）
```

重みは、carrot、potato、wheat、milk が400、egg が450である。

`2e + 500` を1000で割って切り捨てる式は、「0.5点刻みに丸め、ちょうど半分のときは切り上げ」と同じである。e が1.25点（1250）なら、(2500 + 500) / 1000 = 3 で、1.5点になる。

条件の形ごとに、式に入れる値を次のように決める。`sim/ordergen.py` の計算と同じである。

| 条件の形 | 式に入れる産物と数 | 難 |
|---|---|---|
| `exact` | `items` | 半ダースの注文だけ「難」 |
| `total` | `allowed` の1つ目を `total` 個（1種類として数える） | 難 |
| `same` | `pair` のそれぞれを `min` 個 | 難 |

動物の頭数の注文は式を使わず、2頭以上が1.5点、3頭以上が2.5点とする。`include` を付ける場合は0.5点を足し、3点を上限とする（6章）。

### 3.2 共同注文の行

行の点は、その行の産物と数だけを `exact` として、3.1の式で計算する。「難」の加算はない。

## 4. 乱数

### 4.1 乱数生成器

乱数生成器は xoshiro128** とする。内部状態は32ビットの整数4つで、状態を JSON にそのまま保存できる。

ゲームの種は、ゲームの作成時にサーバーが `crypto.getRandomValues` で128ビットを作り、記録の先頭に書く。同じ種から同じゲームを再現できる。

Python の `random`（メルセンヌ・ツイスタ）とは乱数の列が違うため、模擬と1局ずつの一致は求めない（方式設計11.3）。

### 4.2 整数の引き方

`0 以上 k 未満` の整数は、棄却法で偏りなく引く。32ビットの乱数を k で割った余りを使うと、k が2の累乗でないときに小さい値が出やすくなるためである。

サイコロは、1以上6以下の整数を2回引く。シャッフルは Fisher-Yates とする。

### 4.3 乱数を引く順番

BD01 の5章の順で引く。注文と共同注文の生成は、ゲームの乱数生成器から子の生成器を2つ作り（種を2回引く）、それぞれで生成する。

子の生成器に分けるのは、注文の生成の手順を直したときに、盤面やサイコロの乱数の列が変わらないようにするためである。

## 5. 注文の生成

### 5.1 通常の注文（`generated` のとき）

`sim/ordergen.py` の `gen_deck` と同じ手順で、36枚を作る。うち2枚をボーナス注文とする。

生成する型と確率は次のとおり。確率は `gen_one` の分岐をそのまま写す。最初に0以上1未満の乱数 t を引き、t で区分を決める。

| 区分 | 選ばれる条件 | 英文の型 | 条件の形 |
|---|---|---|---|
| 易 | t < 0.35 | `{宛先} needs {産物}.`／`Can you bring me {産物}?`／`{産物}, please.` から1つ | `exact`（1種類、1〜4個） |
| 中 | 0.35 ≤ t < 0.75 | 下の表 | `exact`（2種類） |
| 難 | 0.75 ≤ t | 下の表 | 下の表 |

「中」は、2種類 A、B を選んでから、次の順に決める。

| 型 | 選ばれる条件 | 英文の型 |
|---|---|---|
| 〜ずつ | 乱数 < 0.4 で、A と B がどちらも carrot、potato、egg のどれか | `{宛先} is looking for {A} and {B}, {n} of each.`（n は1〜3） |
| 組み合わせ | 上に当たらず、乱数 < 0.5 | `{宛先} would like {A} and {B}.`（数はそれぞれ1〜3） |
| 否定の罠 | 上のどちらにも当たらない | `Please don’t send {C}. We need {A} and {B}.`（C は A、B 以外の産物。数はそれぞれ1〜3） |

「難」は、0以上1未満の乱数 k で次のように決める。

| 型 | 選ばれる条件 | 英文の型 | 条件の形 |
|---|---|---|---|
| 半ダース | k < 0.3 | `Half a dozen eggs, please.`／`We need half a dozen eggs for the cake.` | `exact`（egg 6） |
| 合計 | 0.3 ≤ k < 0.55 | `We need {n} crops in total. Anything but {X}!` | `total`（X 以外の作物2種類、n は4か5） |
| 同数 | 0.55 ≤ k < 0.8 | `We want the same number of carrots and potatoes, at least two of each.` | `same`（carrot、potato、2） |
| 頭数 | 0.8 ≤ k | `A school class wants to visit a farm with at least {n} animals.` | `animals`（n は2か3）。指定を付けない場合、難易度は「中」 |

産物を選ぶときの重みは、carrot、potato、wheat が1.0、egg と milk が1.8 とする（README の確定仕様の `EGGW=1.8`、`MILKW=1.8`）。

同じ英文の注文は1つの山に1枚までとし、重なったら作り直す。

宛先は8つ（the cafe、the bakery、the school、the pancake shop、the hotel、the hospital、Grandma、the soup kitchen）から選ぶ。英文に宛先が入る型だけ、`to` に宛先を入れる。

`picture` は「易」の注文にだけ付け、その産物とする。

### 5.2 ボーナス注文

5種類から2つか3つを受け付ける種類として選ぶ。英文は次の型とする。

```text
The farmers' market has enough {受け付けない種類を and で並べる}. Bring {受け付ける種類を or で並べる}, as many as you can!
```

種類の並びは carrot、potato、wheat、egg、milk の順にそろえる。`to` は `the farmers' market` とする。

### 5.3 共同注文

8枚を作る。1枚の3行は、egg と milk から1つか2つ、作物から残りの数を選び、並びをシャッフルする。各行の数は、carrot、potato、wheat、egg が2〜4、milk が2〜3とする（確定仕様の `JQSMALL=1`）。

宛先は8つの催し（The village festival ほか、`sim/ordergen.py` の `EVENTS`）から選び、8枚で重ならないように付け替える（`unique_events`）。宛先が重ならないことは、宣言の英文で共同注文を見分けるために要る（ルールブック06章「2枚のどちらか分かれば、名前の一部でよい」）。

英文は `{催し} needs {行1}, {行2} and {行3}.` とする。

### 5.4 印刷用の固定の山（`fixed` のとき）

ルールブック08章の注文36枚と共同注文8枚を、データファイル `app/packages/engine/src/data/fixed_v0_9.json` に書き写して使う。

書き写すときに、各注文の条件を1章の形で表す。ルールブックの「条件」の列との対応は次のとおり。

| ルールブックの書き方 | 条件の形 |
|---|---|
| `milk×4`、`egg×2, potato×2` | `exact` |
| `potato と wheat を合わせて4（ちょうど）` | `total`（allowed は potato と wheat、total は4） |
| `carrot と potato を同じ数ずつ、2つ以上` | `same`（min は2） |
| `動物2頭以上を持っている` | `animals`（min は2、include なし） |
| `egg か milk のどちらか1種類を好きな数` | `bonus`（accepted は egg と milk） |

書き写しの誤りを防ぐため、テストで次を確かめる。

- 各注文の点を3章の式で計算し、ルールブックの点と一致する（付録 A で一致を確かめ済み）。
- 各注文の英文を条件から読んだとき、人が読み取る条件と一致する。この確認は自動化できないため、データファイルを作ったときに一度、人が全36枚を読む。

## 6. 確認事項

ルールブックに定めがない、またはルールブックと移植の元が食い違う事項を挙げる。2026-10-26 に、Q1〜Q4 とも下表の扱いで確定した。

| 番号 | 事項 | 確定した扱い |
|---|---|---|
| Q1 | 動物の頭数の注文に、`sim/ordergen.py` は「そのうち1頭は鳥」のような指定を60%の確率で付け、0.5点を足して「難」にしている。ルールブック v0.9 の印刷用の注文と点の説明にはこの指定がない。模擬の確定仕様の統計は、指定を付けた生成で取られている | 指定を付けない（ルールブックに合わせる）。設定 `animalInclude` で付ける形にも切り替えられるようにする |
| Q2 | 紙の注文カードで、点を表に書くか、折り返しの下に書くか | 折り返しの下として扱い、宣言するまで秘密にする |
| Q3 | 上級者の2倍の支払いで、無料券は1枚で足りるか（BD01 8.4） | 1枚で足りる |
| Q4 | 合計の注文（Anything but）で、許される作物の一方を0個にしてよいか。ルールブックの条件は「potato と wheat を合わせて4（ちょうど）」で、内訳を定めていない | 0個でよい（合計だけを見る） |

Q1 は、ゲームの釣り合いに関わる。指定を付けない場合、動物の頭数の注文が易しくなり、牛やニワトリの方針の勝率が模擬の数値から変わる可能性がある（未検証）。M2 のボットの対局で、指定の有無を両方回して比べる。

## 7. 宣言の英文

### 7.1 数と名詞

数は英語の数詞で書く。1は冠詞（a、an）にする。99まで対応する。

| 産物 | 1つ | 複数 |
|---|---|---|
| carrot | a carrot | {n} carrots |
| potato | a potato | {n} potatoes |
| egg | an egg | {n} eggs |
| wheat | a bag of wheat | {n} bags of wheat |
| milk | a bottle of milk | {n} bottles of milk |

複数の産物は、`A and B`、`A, B and C` と並べる。並びは、注文の英文に出てくる順とする。英文に出てこない産物を出した場合（読み違え）は、carrot、potato、wheat、egg、milk の順で後ろに足す。

### 7.2 行動ごとの英文

ルールブック05章の表の英文を型とする。

| 行動 | 英文 |
|---|---|
| `plant` | I grow potatoes.／I grow wheat.／I grow carrots and feed the soil. |
| `buyAnimal` | I buy a chicken.／I buy a cow and grow grass. |
| `feed` | I feed the chicken.／I feed the cow. |
| `sellProducts` | I sell {産物}.（例 I sell four eggs.） |
| `sellAnimal` | I sell the chicken.／I sell the cow. |
| `deliverOrder` | I sell {産物} to {宛先}.（宛先がない注文は to 以下を付けない） |
| `deliverBonus` | I sell {産物} to the farmers' market. |
| `claimAnimalOrder` | I have {頭数} animals.（頭数は実際の数。1頭なら I have one animal.） |
| `contributeJoint` | I bring {出す産物} to {催し}. |
| `buildHouse` | I build a farmhouse. |

銀行、港、カードと産物の購入、交換には、英文の宣言がない（ルールブック04章、05章）。

### 7.3 英文の表示と記録

組み上げた英文は、スマホの確認画面と大画面の帯に出し（方式設計9.1、9.3）、記録の出来事に残す。

アプリは英文を読み上げの正しさの判定に使わない（方式設計6章）。
