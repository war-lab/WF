# 基本設計 BD06 テスト計画

更新日：2026-10-27

位置づけ：アプリのテストの層、テストケース、合格の基準を定める。

上位の方針は `WORD_FARM_APP_DESIGN_v0.1.md`（以下、方式設計）の11章と12章を正とする。エンジンの仕様は BD01、注文と英文の仕様は BD02、ゲームのルールはルールブック v0.9 を正とする。

## 結論

テストは7つの層で行う。エンジン単体、性質、模擬との照合、サーバーの結合、Playwright による画面を通したテスト（以下 E2E）、実機、試遊前の通しリハーサルである。

エンジン単体のテストケースは、4章に ID 付きで列挙する。ルールブック10章の「よくある質問」33問は、すべてテストケースか、テスト以外の確かめ方に対応させた（付録 A）。

性質のテストは、`legalActions` が返す操作から乱数で選んでゲームを進め、BD01 4章の不変条件を毎回確かめる。コマンドの列を「操作の一覧の何番目を選んだか」の列で表し、縮小しても正しい操作の列のままになるようにする。

模擬との照合は、模擬の1局の記録をエンジンのコマンドの列に写して再適用し、手番ごとに状態を比べる。4人戦と3人戦の各1600局で、最後の手番まで食い違いがないことを合格とする（5.5）。

模擬とアプリで扱いの違う点は、模擬に切り替え（`APPRULES=1`）を足してアプリに合わせた（5.5.2）。

実機のテストは、Cloudflare にデプロイした版に、会社のPCと各自のスマホのモバイル通信からつないで行う（方式設計2章）。

## 1. テストの層

| 層 | 対象 | 防ぐもの | 実行の時機 |
|---|---|---|---|
| エンジン単体 | `engine` の関数 | ルールの読み違い、境界の誤り、拒否の漏れ | 保存のたび、コミットの前 |
| 性質 | `engine` 全体 | 個別のケースで想定していない状態での不変条件の破れ、非決定性、秘密の漏れ | コミットの前（少ない回数）、毎晩（多い回数） |
| 模擬との照合 | `engine` と模擬 | 単体のテストを通る、細かな処理の順番の誤り（例：時間切れを数える手番）。模擬とアプリのルールの読み違い | M2 の完了時、ルールの変更時（1600局）。`npm test` で8局 |
| サーバーの結合 | `worker`、`protocol` | 二重の適用、保存と復旧の誤り、秘密の情報の送信、管理操作の権限 | コミットの前 |
| E2E | 画面、サーバー、エンジン | 画面と通信をつないだときの誤り、同時の入力、再接続 | M4 以降のコミットの前 |
| 実機 | スマホ、ホストPC、ネットワーク、Cloudflare | 消灯、会社のネットワークとモバイル通信での接続、読みやすさ、無料プランの使用量 | M5、試遊の前 |
| 通しリハーサル | 全体と運用 | 当日の手順の抜け、所要時間の見積もりの外れ、記録の書き出しの失敗 | 第1回試遊の前 |

単体と性質のテストを分けるのは、両者が防ぐものが違うためである。単体のテストは「この状況でこうなる」を確かめ、ルールの読み違いを見つける。性質のテストは、人が思いつかない状態の組み合わせで、不変条件が破れないかを確かめる。

E2E は、手動の結合テストの代わりにはならない。実機のテストと通しリハーサルは、E2E で網羅できない、端末と人の振る舞いを確かめるために置く。

## 2. テストの道具と書き方

| 層 | 道具 |
|---|---|
| エンジン単体、性質 | Vitest、fast-check |
| 模擬との照合 | Python の模擬の記録（`sim/record.py`）、Node.js の再適用（`app/packages/engine/tools/replay.ts`、`compare.ts`） |
| サーバーの結合 | Vitest。部屋の処理（`room.ts`）の単体テストは `node:sqlite` と偽の接続で、Durable Object の結合テストは Miniflare（esbuild でまとめた Worker を手元の workerd で動かす）で行う（6章） |
| E2E | Playwright（Chromium、WebKit） |

エンジン単体のテストは、状態を一から組み立てる補助の関数（以下、状態の組み立て器）を使って書く。ゲームの最初から操作を積み重ねて状態を作ると、テストが前提の操作の誤りに引きずられるためである。

状態の組み立て器は、組み立てた状態が BD01 4章の不変条件を満たすことを、組み立ての最後に確かめる。不変条件を破った状態からのテストは、実際には起きない状態を試すことになるためである。

乱数に依存するテストは、種を固定するか、`dice: manual` で出目を指定する。

### 2.1 期待値の書き方

期待値は、原則としてルール設定（`config`）から計算して書く。例えば初期のコインは `config.seatCoins[席]` と比べる。試遊のあとでルールの数値を変えても、テストが仕様の変更として赤にならないようにするためである。

ルールブック v0.9 の具体的な値そのものを確かめるケースは、ID の末尾に `F` を付けて分ける（例 TC-SET-15F）。これらは、ルール設定の既定値が v0.9 の値であることと、印刷用のデータの書き写しを確かめる。ルールの数値を変えたときに赤になるのは `F` の付いたケースだけで、赤の理由が仕様の変更か退行かを、ID だけで切り分けられる。

### 2.2 書く順番

エンジンのテストは、次の順で書く。

1. 状態の組み立て器と、その不変条件の確かめ
2. 性質のテスト（5章）。不変条件と「`legalActions` が出した操作は `apply` で受け付けられる」
3. ルールブック10章のよくある質問に対応するケース（付録 A）
4. 拒否の理由のケース。前提、コマンド、符号の3列の表として書き、1つのテストの関数で回す（表駆動）

性質のテストを先に置くのは、個別のケースを書く前に、境界の誤りと不変条件の破れを早く見つけるためである。件数は減らさない。順番だけを決める。

### 2.3 E2E を途中の場面から始める口

E2E は、試験用の起動の設定でだけ有効になる「状態の読み込み」の口を使い、途中の場面（例：ラウンド3の初め、7の出目の直前）から始められるようにする。最初から操作を積み重ねると、1本のシナリオが長くなり、前提の操作の失敗に引きずられるためである。

この口は、6章の障害注入の口と同じく、通常の起動では無効にする。通常の起動で口が無効であることは TC-SRV-17 で確かめる。

## 5. 性質のテストと模擬との照合

### 5.1 生成器

性質のテストの入力は、次の3つの組とする。

- 種（128ビット）と人数（3か4）
- 選択の列：0以上の整数の列。i 番目の値を、その時点の操作の候補の数で割った余りで、候補を選ぶ
- 乱入の列：不正なコマンド（乱数で作った形だけ正しいコマンド）を挟む位置と内容

操作の候補は、`legalActions` の `enabled: true` の操作、問いへの答えの候補、手番でない人の交換の申し出と日本語の支払いを合わせたものとする。

選択の列の値は、1つの操作に1つを使う。候補はその値の剰余で選び、売る数などの細かい値は、その値を種にした乱数で決める。

ゲームごとに、操作の選び方を次の3つから選ぶ。候補から一様に選ぶと、注文がほとんど成立せず、全局が注文切れで終わり、目標点での勝ちや共同注文の完成に届かないためである（2026-11-06 のレビューで200局を数えて確かめた）。

| 選び方 | 内容 |
|---|---|
| 一様 | 候補から一様に選ぶ |
| 優先 | 点や物が増える操作（植える、動物を買う、餌をやる、条件を満たす届け、共同注文の行、産物の購入）を優先して選ぶ |
| 優先と管理 | 優先に加えて、低い確率で管理の操作（`callLastRound`、`abortGame`、`answerFor`、`endTurnFor`）を選ぶ |

コミットの前の回数（5.2）では、全局の終わりに、目標点での勝ち、注文切れ、ホストの宣言、中止の各終わり方と、共同注文の完成、動物の頭数の注文の成立が、それぞれ1回以上起きたことを確かめる。

選択の列で操作を表すのは、fast-check が値を小さくしても、各値が常に候補のどれかを指すためである。コマンドそのものの列を縮小すると、途中のコマンドが不正になり、縮小の結果が意味を持たなくなる。

### 5.2 回数

| 実行の時機 | ゲームの数 | 1ゲームの上限 |
|---|---|---|
| コミットの前 | 200 | 3000操作 |
| 毎晩 | 5000 | 3000操作 |

上限を超えたら失敗とする。乱数で選ぶ操作では、注文が届かないまま進むことが多いが、注文は時間切れで山から減るため、有限の手番で注文切れになり終わる。4人戦なら、36枚が3枚ずつ12手番ごとに流れるとして、およそ150手番で尽きる見込みである（計算による見積もりで、実測していない）。

### 5.3 確かめる性質

各操作のあとに、次をすべて確かめる。

1. BD01 4章の不変条件1〜8
2. 拒否されたコマンドの前後で、状態が完全に一致する
3. `legalActions` の `enabled: true` の操作は、`apply` で受け付けられる
4. `viewFor(state, "board")` が、手札の中身、伏せた注文、表の注文の `cond` と `hp`、乱数の状態を含まない
5. `viewFor(state, 席)` が、ほかの人の手札の中身を含まない

各ゲームの終わりに、次を確かめる。

6. 記録したコマンドの列を最初から再適用すると、同じ最終状態になる
7. `phase` が `over` で、`result` の `ranking` に全員がいる

BD01 4章の不変条件（9番目の「表の共同注文は、3行そろっていない」を含む）を確かめる。3行そろった時点で完成して捨てるため、そろったまま表に残る状態は誤りである。

### 5.4 縮小

fast-check の既定の縮小を使う。失敗した入力は、種と選択の列を JSON でファイルに書き出し、エンジン単体のテストとして固定する。同じ誤りが戻らないようにするためである。

### 5.5 模擬との照合

模擬との照合は、模擬の1局の記録をエンジンのコマンドの列に写して再適用し、手番ごとに状態を比べる方式で行う（以下、再適用の照合）。方式設計11.3 の方式である。

統計で比べる方式（ボットを移植し、両方で多数の局を回して平均を比べる）は、2026-11-06 にやめた。両者の乱数の列が違うため1局ずつは比べられず、ラウンド数の平均で約4%以上の差がないと誤りを見つけられない見込みだったためである（M1 のレビューでの試算。未検証）。再適用の照合は、1手番の食い違いでも、最初に食い違った手番とコマンドを示す。ボットの TypeScript への移植も要らない。

注文の生成と盤面の作り方は、再適用の照合の対象外である。山と盤面を記録から入れるためである。これらは 4.15（TC-GEN）と3章（TC-BRD）で確かめる。

#### 5.5.1 手順

1. 模擬の記録の道具（`sim/record.py`）が、確定仕様（設計メモ 付録 A）に `APPRULES=1`（5.5.2）を加えた条件で1局を回し、JSON に書き出す。
2. 再適用の道具（`app/packages/engine/tools/replay.ts`）が、`createGame` で作った状態の盤面と山を、記録の値に置き換える。サイコロは `manual` にし、出目を `inputDice` で入れる。
3. 拠点の配置を `placeHouse` で送り、問いには記録の選択で答え、出来事を対応するコマンドで送る（下の表）。
4. 手番ごとに、収入のあとと行動のあとの2つの時点で状態を比べる。
5. 拒否されたコマンドか、食い違った項目があれば、その局はその手番で止め、内容を報告する。

記録の中身は次のとおりである。

| 項目 | 中身 |
|---|---|
| 初期の状態 | タイルの種類と数字、港、席ごとのコイン、注文と共同注文の山（引く順）、拠点を置いた順と交点 |
| 選んだカード | 席ごとの列。準備の分と、手番ごとの分に分ける。seed と animal の収入、7の市場の日、救済、3人戦の追加の1枚 |
| 手番ごと | 出目、出来事の列、2つの時点の写し |

比べる項目は、各席の手札、産物、コイン、点、区画、拠点と、表の注文、表の共同注文と出した行、2つの山の残りの枚数、終わったかどうかである。

手番の終わりの処理のあとでは比べない。アプリは `endTurn` の中で、次の手番の始まり（注文の公開、時間切れ）まで進めるためである。次の手番の収入のあとの比較で、両方の処理の結果を比べることになる。

模擬の出来事は、次のコマンドに写す。

| 模擬の出来事 | コマンド |
|---|---|
| `plant`、`buy`、`feed`、`animal_sell`、`market` | `plant`、`buyAnimal`、`feed`、`sellAnimal`、`sellProducts` |
| `deliver` | 注文の種類により `deliverOrder`、`deliverBonus`、`claimAnimalOrder` |
| `joint_line`、`house` | `contributeJoint`、`buildHouse` |
| `bank` | 交換の比率により `bankTrade` か `harborTrade`（自分の拠点の港） |
| `coinbank`、`prodbuy` | `buyCard`、`buyProduct` |
| `trade` | 手番の人の `proposeTrade` と、相手の `respondTrade`（承諾） |
| `seven_discard` | 捨て札の問いの答え（模擬が捨てたカード） |

収入、市場の日、救済、収穫、補充、時間切れ、勝ちは、コマンドに写さない。エンジンが処理した結果を、写しで比べる。

#### 5.5.2 模擬をアプリにそろえる差

模擬の確定仕様には、アプリと扱いの違う点がある。`APPRULES=1` のとき、模擬は次の点をアプリ（ルールブック）に合わせる。

| 差 | 確定仕様の模擬 | `APPRULES=1` の模擬とアプリ |
|---|---|---|
| 単語カードの山 | 無限に配る | 枚数を持つ（ルールブック09章）。尽きた種類は配らず、銀行でも取れない |
| 救済 | 収入の出目に自分のタイルがなければ出す | 実際に1枚も受け取らなかったときに出す（山が尽きて配られなかった場合を含む） |
| 配る順 | タイルの番号の順。7の市場の日は席0から | 手番の人から時計回りに、拠点を置いた順、交点に接するタイルの番号の順。市場の日も手番の人から |
| 選んだ山が尽きたとき | 起きない | 残っている種類から選び直す（アプリの問いの出し直し、BD01 7.2） |
| 通常の注文の時間切れの時機 | 数える人の次の席の手番の初め | 数える人の手番の終わり。最後の席の手番で注文が尽きたとき、次のラウンドを回さずに終える |
| 注文切れで終わるときの、未完成の共同注文の半分の点 | 払わない | 払う（ルールブック01章） |

次の2つは模擬の不具合として、`APPRULES` によらず直した。どちらも局が終わったあとの処理で、勝者とラウンド数は変わらない。

- 勝ったあとも、同じ手番の中で交換と銀行の操作を続けていた
- 手番の初めに勝ったあとも、出目を振って収入を配っていた

次の差はそろえていない。

| 差 | 照合での扱い |
|---|---|
| 動物の頭数の注文の指定（模擬は付け、アプリの既定は付けない。BD02 Q1） | 再適用は記録の山を使うため、照合には影響しない。釣り合いへの影響は 5.5.5 で測った |
| 共同注文の時間切れの処理の時機（模擬は次の手番の初め、アプリは数える人の手番の終わり） | 処理の結果は、次の手番の収入のあとの比較で同じになる。勝ちの判定はどちらも、点を得た人の次の自分の手番の初めに行う |
| 問いを出す時点（アプリは配る前に全員に問い、模擬は配りながら選ぶ） | 前の人が山の最後の1枚を取ると、模擬は選ばないが、アプリは問う。再適用では仮の答えを入れ、配られないことを写しで確かめる |
| ボーナス注文の英文の重複 | 記録の山を使うため、照合には影響しない |
| 70分の打ち切り | どちらにもない。`callLastRound` は送らない |

#### 5.5.3 局数と合格の基準

4人戦と3人戦を各1600局（種1〜1600）回し、全局で最後の手番まで食い違いがないことを合格とする。`npm run compare` で回す（python が要る）。

回帰を防ぐため、同じ記録の8局（4人戦と3人戦の種1〜4）を `app/packages/engine/test/fixtures/sim` に置き、`npm test` で再適用する（TC-CMP-01）。模擬のボットかルールを変えたら、記録を作り直す。

2026-11-06 に、3200局（比べた手番は計145,270）がすべて最後の手番まで一致し、合格した。記録に約3分、再適用に約5分かかった。

山が尽きたことによる問いの出し直しにあたる場面（前の人が山の最後の1枚を取り、答えた種類が配られなかった問い）は、3200局中10局で計11回だった。

#### 5.5.4 照合が誤りを見つける力

エンジンに次の誤りを1つずつ入れ、4人戦と3人戦の各400局で再適用した。どの誤りも、多くの局で食い違いとして見つかった。

| 入れた誤り | 食い違った局 |
|---|---|
| 7の捨て札の条件を「7枚以上」から「8枚以上」にする | 800局中663局 |
| 共同注文の半分の点を切り捨てから切り上げにする | 800局中724局 |
| 通常の注文の時間切れまでの手番の数を1つ増やす（ラウンド3の公開分） | 800局中746局 |

#### 5.5.5 そろえた差と指定の有無による統計の変化

`APPRULES=1` は模擬のルールを変えるため、設計メモの統計（付録 A-14）からの変化を `sim/probe_apprules.py` で測った。各1600局、局の種と方針の割り当ては照合と同じである。±は95%信頼区間の半分の幅である。

| 指標 | 確定仕様 | `APPRULES=1` | `APPRULES=1`、指定なし |
|---|---|---|---|
| 4人戦のラウンド数 | 11.80±0.18 | 11.75±0.17 | 11.87±0.16 |
| 3人戦のラウンド数 | 15.37±0.23 | 15.44±0.22 | 15.26±0.22 |
| 4人戦の席ごとの勝ち | 389 / 440 / 395 / 376 | 384 / 416 / 420 / 380 | 383 / 396 / 429 / 392 |
| 3人戦の席ごとの勝ち | 564 / 544 / 491 | 550 / 538 / 512 | 561 / 557 / 482 |
| 4人戦の方針ごとの勝率（作物、ニワトリ、牛、混合） | 18.2%、26.1%、26.3%、29.2% | 18.6%、26.2%、25.3%、29.7% | 18.8%、25.7%、27.7%、27.6% |

## 7. E2E

Playwright で、手元で動かした Workers の実行環境（`wrangler dev`）に、大画面1つとスマホ4つを別のブラウザのコンテキストとしてつなぐ。スマホは端末の模擬（iPhone と Pixel の画面の大きさ）で開く。大画面のコンテキストにだけホストの鍵を入れ、管理操作の制限を確かめる。

乱数の種は固定し、出目が要る場面は `dice: manual` で指定する。

## 9. 試遊前の通しリハーサル

第1回試遊の前に、開発者を含む3〜4人で、当日と同じ機材と場所で1局を通す。

確かめるのは次のとおり。

- 準備の手順（PCの起動から最初の手番まで）の所要時間
- ルールの説明からゲームの終わりまでの所要時間と、1手番の時間
- 記録の書き出しと、その中身が設計メモ5章の確認に使えること
- アプリが止まったときに、紙の道具に切り替えられること

リハーサルで見つかった問題は、重大度を付けて記録し、重大なものを直してから試遊を行う。
