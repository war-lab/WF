# 基本設計 BD05 サーバー、保存、運用

更新日：2026-10-26

位置づけ：ホストPCで動かすサーバー（`app/packages/server`）の内部構成、保存の形式、時計、起動と運用の手順、記録の書き出し、非機能の目標を定める。

上位の方針は `WORD_FARM_APP_DESIGN_v0.1.md`（以下、方式設計）の7章、8章、10章を正とする。エンジンの型とコマンドは BD01、注文と乱数は BD02 を正とする。

## 結論

サーバーは1プロセスで1つの部屋だけを持つ。1台のホストPCで1つのテーブルを囲む使い方では、部屋を複数持つ利点がない。

状態を変える処理は、すべて1本のキューで1つずつ行う。コマンドはエンジンで判定してから、受け付けたものだけをファイルに追記し、ディスクへの書き出し（fsync）を待ってから、状態を確定して `ack` を返す。

復旧は、記録の先頭からすべてのコマンドを再適用して行う。状態のスナップショットは保存しない。手番の終わりごとに、そのときの状態のハッシュを照合の行として記録に書き、再適用の結果が保存時と同じかを確かめる。1局のコマンドは500〜1000件と見積もり、純粋な関数の再適用は短時間で終わる見込みである（未検証。M1 で測る）。

再適用でコマンドが1件でも拒否されたり、照合が合わなかったりしたら、自動では進めずに止める。記録を作ったエンジンと今のエンジンの判定が違うことを意味するためで、旧エンジンに戻して再起動する。

取り消しは記録を書き換えず、取り消しの行を追記する。有効なコマンドの列は、記録から取り消された行を除いて求める。サーバーが発したコマンド（`markTimeUp`、`pause`、`resume`）は取り消しの対象にしない。

記録の書き込みに失敗したら、ファイルを書き込む前の長さまで切り詰める。切り詰めにも失敗したら、再起動まですべてのコマンドを拒否する。

ゲームの時計は単調時計で数え、壁時計（PCの時刻）は表示と記録にだけ使う。PCのスリープなどで時計が飛んだ場合は、自動で一時停止してホストに知らせる。

会社のPCでサーバーを起動してよいか、ファイアウォールとモバイルホットスポットの設定を変えてよいかは、社内規程の確認が済んでいない（方式設計14.2）。運用の手順は、許可が得られる前提で書く。

## 1. 内部構成

### 1.1 部品

| 部品 | 役割 |
|---|---|
| HTTP | 画面のファイル（ビルド済みの静的ファイル）を配る。QRコードの画像を返す |
| 接続の管理 | WebSocket の接続と、参加者、席の対応を持つ。1つの席には最後につないだ1本だけを有効にする |
| 部屋 | 部屋のコード、参加者、ゲームの状態、`rev` を持つ。1プロセスに1つ |
| キュー | 状態を変える要求を1つずつ処理する（1.2） |
| エンジン | BD01 の `apply`、`viewFor`、`legalActions` を呼ぶ |
| 保存 | 記録の追記、照合の行、席の対応の書き出し（2章） |
| 時計 | ゲームの経過を数え、`markTimeUp` を出す（3章） |
| 記録の書き出し | 記録を再適用して出来事を作り、試遊の記録を作る（5章） |
| 管理の門番 | 管理操作を、ホストPC自身（ループバックのアドレス）からの接続に限る |

管理の門番は、WebSocket の接続元アドレスがループバックの場合だけ `admin` のメッセージを受け付ける。大画面ビューを参加者のスマホで開いても、管理操作はできない（方式設計3章）。

実装では次の4点を守る。どれかが欠けると、門番を外から越えられる。

- 接続元のアドレスは、ソケットの `req.socket.remoteAddress` から取る。HTTP のヘッダ（`X-Forwarded-For`、`Host`）は使わない。
- Fastify の `trustProxy` は無効にする。有効だと、参加者が `X-Forwarded-For: 127.0.0.1` を付けて接続し、ループバックを装える。
- アドレスは正規化してから比べる。IPv6 で待ち受けると、IPv4 のループバックは `::ffff:127.0.0.1` で届く。`127.0.0.1`、`::1`、`::ffff:127.0.0.1` をループバックとする。
- 管理の接続では、WebSocket の `Origin` ヘッダが、このサーバー自身のオリジン（`http://localhost:8787` など）であることを確かめる。WebSocket には CORS の制限がかからないため、ホストPCのブラウザで開いたほかのサイトが `ws://localhost:8787` に接続し、管理操作を送れてしまう。

### 1.2 キューの処理の順番

キューは、端末のコマンド、管理操作、時計の発する `markTimeUp` と一時停止、参加と席の変更を、届いた順に1つずつ処理する。

Node.js は1本のスレッドで動くが、ファイルの書き出しを待つ間に次の要求の処理が始まると、2つのコマンドが同じ古い状態を元に判定される。キューはこれを防ぐ。

1つのコマンドの処理は次の順で行う。

1. 形を zod で確かめる。合わなければ `reject`（`BAD_MESSAGE`）を返す。
2. `id` が処理済みの表にあれば、前回の結果（`ack` か `reject`）をそのまま返し、終える。
3. エンジンの `apply` を呼ぶ。拒否なら `reject` を返し、処理済みの表に結果を入れて終える。拒否は記録に追記しない。
4. 受け付けたなら、`rev` を1増やした値で、記録の1行（2.3）を作って追記し、fsync を待つ。手番の終わり（出来事 `turnEnded`）なら、続けて照合の行（2.4）も追記してから fsync する。
5. 書き出しに失敗したら、状態を確定せず、`reject`（`STORAGE_ERROR`）を返す。大画面に保存の異常を出す。続けて2.5の手順で、ファイルを書き込む前の長さまで切り詰める。
6. 状態を新しいものに置き換え、処理済みの表に `ack` を入れる。
7. `ack` を送り主に返す。
8. 接続しているすべての端末へ、その端末向けの `view` と出来事を送る。

手順3で状態を変えずに判定できるのは、エンジンが純粋な関数だからである。判定の前に記録すると、拒否されたコマンドまで記録に残り、再適用のたびに拒否をやり直すことになる。

手順1の `BAD_MESSAGE` は、`cmd` の中のコマンドの形が誤っている場合の返し方である。`cmd` 以外のメッセージの形の誤りには `error` を返す（BD03 3.8）。

## 2. 保存

### 2.1 置き場所

```text
app/data/
  games/
    2026-11-05T1830_4821/        <開始の日時>_<部屋のコード>
      meta.json                  ゲームの前提（2.2）
      seats.json                 参加者、席、トークン（2.6）
      commands.jsonl             受け付けたコマンド、取り消し、照合の記録（2.3、2.4）
      clock.json                 時計の控え（3.3）
      export/                    試遊の記録の書き出し（5章）
      server.log                 動作の記録（6.1）
  current.json                   続きを遊ぶゲームのフォルダ名
  lock                           二重起動を防ぐ印（2.10）
```

`app/data/` はリポジトリに含めない（`.gitignore` に入れる）。参加者の名前とトークンを含むためである。

### 2.2 meta.json

ゲームの作成時に1回だけ書き、以後は書き換えない。

```json
{
  "format": 1,
  "gameId": "2026-11-05T1830_4821",
  "createdAt": "2026-11-05T18:30:12.345+09:00",
  "engineVersion": "0.1.0+3f2a9c1",
  "rulesVersion": "0.9",
  "config": { "...": "BD01 3章のルール設定。既定値から変えた項目も含めた全量" },
  "seed": "9f1c0a7b3e5d4c2a8b6e1f0d9c7a5b3e",
  "n": 4
}
```

`engineVersion` は、パッケージの版と git のコミットの短い番号を並べたものである。復旧の際に、記録を作ったエンジンと今のエンジンが違うことを検出するために使う（2.7）。

`seed` は、ゲームの再現に要る。表示はしない。ゲームの途中に知られると、伏せた注文の山の順番を計算で求められてしまうため、保存のファイルはホストPCの外に出さない。

### 2.3 commands.jsonl

受け付けたコマンド1件を1行とする。行は追記するだけで、書き換えも削除もしない。

```json
{"seq":57,"rev":61,"at":"2026-11-05T18:42:10.123+09:00","elapsedMs":731204,"id":"5b0e8d1f2a7c4e96a13f07c2d9e4b851","actor":{"k":"seat","seat":2},"cmd":{"t":"deliverOrder","orderId":"o07","items":{"carrot":3}},"meta":{"sentenceShown":false}}
```

| 項目 | 内容 |
|---|---|
| `seq` | 記録の行の通し番号。1から始まり、取り消しの行も含めて1ずつ増える |
| `rev` | この行を適用したあとの `rev`（2.8） |
| `at` | 壁時計の時刻。記録の読みやすさのためで、再適用には使わない |
| `elapsedMs` | ゲームの経過時間（3章）。手番の時間の集計に使う |
| `id` | コマンドの一意の値。128ビットの16進表記（32文字）。サーバーが発したコマンドも同じ形で、出どころは `actor` で区別する（BD03 3.2） |
| `actor` | `{"k":"seat","seat":n}`、`{"k":"admin"}`、`{"k":"server"}` のどれか |
| `cmd` | BD01 のコマンド。ゲームの作成（`createGame`）も1行目のコマンドとして残す |

取り消しの行は次の形とする。

```json
{"seq":64,"rev":68,"at":"...","elapsedMs":790311,"id":"1c9e0b7a4d2f8e6c5a3b1d9f7e5c3a10","actor":{"k":"admin"},"undo":{"seqs":[60,61,63]}}
```

`undo.seqs` は、この取り消しで無効にした行の `seq` の一覧である。取り消したいコマンドと、そのあとに入って巻き込まれたコマンドを並べる（方式設計8.2）。`actor` が `server` の行（`markTimeUp`、`pause`、`resume`）は並べない（2.9）。上の例では、62 がサーバーの行で、取り消しの対象から外れている。

### 2.4 照合の行

手番の終わり（出来事 `turnEnded`）のコマンドの行の直後に、照合の行を追記する。

```json
{"check":{"afterSeq":212,"turnSerial":12,"stateHash":"sha256:…"}}
```

`stateHash` は、そのときの `GameState` を正規化した JSON（キーを辞書順に並べる）のハッシュである。参加者の名前は `GameState` に入らないため（5.3）、ハッシュにも名前は入らない。

照合の行は、状態を戻すためには使わない。復旧と取り消しで再適用したときに、同じ時点の状態のハッシュと比べて、エンジンの判定が変わっていないことを確かめるために使う（2.7）。取り消しのあとは、取り消された行より後ろの照合の行は比べない。有効な列が変わり、同じ時点の状態が変わるためである。

状態の全量のスナップショットは保存しない。復旧を常に先頭からの再適用で行うため、スナップショットは近道として使わず、エンジンの変化の検出には照合の行で足りる。

出来事の記録（`events.jsonl`）も保存しない。出来事は記録の再適用で作り直せるため、記録の書き出し（5章）の際に再適用して作る。出来事の名前は次の40個とする。中身の項目と通し番号（`eventSeq`）は BD03 で定める。

gameCreated, seatsAssigned, housePlaced, cardsGranted, promptsOpened, promptAnswered, diceRolled, cardsDiscarded, harvested, planted, animalBought, fed, productsSold, animalSold, orderDeclared, orderSucceeded, orderFailed, ordersRevealed, orderExpired, jointRowFilled, jointCompleted, jointExpired, houseBuilt, bankTraded, harborTraded, cardBought, productBought, tradeProposed, tradeAccepted, tradeDeclined, tradeWithdrawn, japanesePaid, turnStarted, turnEnded, endFlagged, timeUp, paused, resumed, gameOver, undone

`undone` だけはエンジンではなくサーバーが出す（2.9）。

### 2.5 書き込みに失敗したとき

追記する前に、`commands.jsonl` の長さを控えておく。追記か fsync に失敗したら、次の順で処理する。

1. ファイルを控えた長さまで切り詰め（`ftruncate`）、fsync する。途中まで書けた行がファイルに残ると、次の行がその後ろに続き、復旧の読み取りが止まるためである。また、`reject` を返したコマンドが、再起動の再適用で復活することを防ぐためでもある。
2. 切り詰めにも失敗したら、保存を止めた状態（fail-stop）にする。再起動まで、すべてのコマンドを `STORAGE_ERROR` で拒否し、大画面に「保存できません。サーバーを再起動してください」と出す。保存できないまま続けると、落ちたときに戻せないためである。

### 2.6 seats.json

部屋のコード、参加者、席、トークンを持つ。変わるたびに、一時ファイルに書いて fsync し、名前を変えて置き換える。書きかけのファイルが残らないようにするためである。

名前の変更（rename）は、Windows では、ウイルス対策の実時間スキャンや索引付けがファイルを開いていると、`EPERM` や `EBUSY` で失敗することがある（この PC では未検証）。失敗したら、短い間隔（50ミリ秒から倍にして最大1秒）で、合計5秒まで再試行する。それでも失敗したら、保存の異常として大画面に出す。

```json
{
  "format": 1,
  "roomCode": "4821",
  "clockwise": ["p1", "p3", "p2", "p4"],
  "participants": [
    { "participantId": "p1", "name": "Aki", "seat": 0, "color": "red", "tokenHash": "sha256:…", "japaneseRate": 1 }
  ]
}
```

トークンはハッシュだけを保存する。保存のファイルを見ただけでは、他人の席に入れないようにするためである。トークンそのものは、発行の時にスマホへ1回だけ送る。

参加者の名前は、このファイルとロビーの状態にだけ置く。エンジンの状態（`GameState`）は `participantId` だけを持ち、名前は持たない。名前は、サーバーが `view` を作るときに付ける（BD03 1.3）。

### 2.7 復旧

サーバーの起動時に `current.json` が指すゲームがあり、終わっていなければ、次の手順で戻す。

1. `meta.json`、`seats.json` を読む。
2. `commands.jsonl` を読み、最後の行が途中で切れていれば、その行を捨てる。末尾が NUL の文字で埋まっている行も、切れた行として扱う。電源が落ちたあと、ファイルの末尾が NUL で埋まることがあるためである（Windows の NTFS で起こりうる。未検証）。切れた行は fsync が終わる前に落ちた行で、`ack` を返していないため、端末は再送する（BD03 3.5）。
3. 取り消しの行から、有効な行の列を求める。
4. 有効な行の列を、先頭から再適用する。照合の行に当たったら、その時点の状態のハッシュと比べる（取り消しのあとで比べない行は2.4のとおり）。
5. 処理済みの `id` の表を、すべての行（取り消された行も含む）から作る。取り消されたコマンドの再送を、もう一度適用しないためである。
6. `rev` を、記録の最後の行の `rev` にする。起動ごとの `bootId` を新しく作る（2.8）。
7. エンジンに `pause(at)` をサーバーのコマンドとして適用し、記録してから、接続を受け付ける。時計も止めたままにする（3.3）。ホストが大画面で再開を押すまで、スマホの操作は `PAUSED` で拒否される。

時計だけを止めてエンジンを止めないと、再開を押す前でもスマホの操作が通り、その間の経過が数えられない。手順7でエンジンにも一時停止を記録するのはこのためである。

手順4で、コマンドが1件でも拒否されたか、照合が合わなかった場合は、エンジンの判定が記録を作った時と変わったことを意味する。自動では進めず、止まったまま、大画面に次を出す。

- 拒否された行の `seq`、コマンド、拒否の理由。または照合が合わなかった手番。
- 記録を作ったエンジンの版（`meta.json` の `engineVersion`）と、今のエンジンの版。
- 対処の手順：記録を作ったエンジンの版の git のコミットを取り出し（`git checkout <コミット> -- app`）、`npm ci` と `npm run build` をやり直して再起動する。

拒否された行を飛ばして続ける選択肢は作らない。飛ばすと、その行の結果を前提にしたあとの行（交換など）の意味が変わり、誰も意図していない状態ができるためである。

`engineVersion` が `meta.json` と同じでも、手順4の拒否と照合は必ず確かめる。試遊の当日にエンジンを直した場合に、気づかずに違う結果で続けることを防ぐためである。

### 2.8 rev の扱い

`rev` は、状態を変えるたびに1ずつ増やす通し番号で、取り消しでも戻さない（方式設計7.3）。

- コマンドを受け付けたら1増やす。
- 取り消しを行ったら1増やす。状態は前に戻っても、`rev` は進む。
- 参加者と席の変更（ロビー、席の再発行）も1増やす。
- 接続の状態（`connected`）の変化では増やさない。取り消しの `undoCommit` の照合を、誰かの再接続で崩さないためである。

記録の各行に、適用後の `rev` を書く（2.3）。復旧では最後の行の値を引き継ぐ。

ただし、ロビーや席の再発行の変更は記録に残らないため、再起動をまたぐと `rev` が戻ることがある。そこでサーバーは起動のたびに `bootId`（乱数）を作り、`view` に付ける。端末は `rev` を同じ `bootId` の中でだけ比べ、`welcome` の直後の最初の `view` は無条件に受け入れる（BD03 3.3）。

### 2.9 取り消しの手順

取り消しは、管理操作の `undoPreview` と `undoCommit` の2段階で行う。

1. ホストが「1つ取り消す」を押すと、サーバーは有効な行の最後から、手番の人のコマンドを取り消す対象に選ぶ。`undoPreview` に `seq` を付けた場合は、その行を対象にする。
2. 対象より後ろの有効な行のうち、`actor` が `server` でない行を、巻き込まれる行として並べる。
3. 対象と巻き込まれる行を、人が読める形（「Ben：日本語の支払い（単語、1コイン）」など）で大画面に出す（`undoPreview`）。
4. ホストが確かめて実行を押すと（`undoCommit`）、取り消しの行を追記して fsync を待つ。
5. 有効な行の列を、先頭から再適用し、状態を置き換える。サーバーの行（`markTimeUp`、`pause`、`resume`）は、取り消した行を除いた列の中で、元の順番のまま再適用する。
6. `rev` を1増やし、全端末に `view` を送る。出来事 `undone`（BD03 で定める）で、取り消されたことを大画面に出す。

手順3と4の間に別のコマンドが入った場合は、`undoCommit` を拒否し、もう一度 `undoPreview` からやり直させる。巻き込みの一覧を見たあとに対象が増えると、確かめた意味がなくなるためである。そのため `undoCommit` には、`undoPreview` の時点の `rev` を付けて送り、一致を求める。

取り消しで状態が戻っても、出された問いや交換の申し出は、戻した状態に含まれるものだけになる。消えた申し出は、各スマホで表示から消える。

サーバーの行を取り消しの対象から外すのは、時計とエンジンの状態を食い違わせないためである。

- `markTimeUp` を取り消すと、エンジンの `timeUp` が偽に戻る。サーバーは70分の発火を済ませているため送り直さず、時間でゲームが終わらなくなる。
- `pause` だけが取り消されると、エンジンは進行中、時計は停止という食い違いになる。`resume` だけが取り消されると、時計は進むのに、すべてのコマンドが `PAUSED` で拒否される。

サーバーの行は、前の行の結果に依存しない（`markTimeUp` は `timeUp` を真にするだけ、`pause` と `resume` は `paused` を切り替えるだけ）。そのため、取り消した行を除いた列で再適用しても意味が変わらない。

### 2.10 二重起動の防止

サーバーは起動の最初に、`app/data/lock` をファイルが無いときだけ作る方法（`fs.open` のフラグ `wx`）で作り、中にプロセスの番号と起動の時刻を書く。作れなければ、すでに別のサーバーが動いているとして、何も書かずに終わる。

`npm start` を2回実行した場合に、2つのプロセスが同じ記録に追記するのを防ぐためである。ポートの待ち受けの失敗は、復旧や `clock.json` の書き込みより後に起きることがあり、それだけでは防げない。

正しく終わったときは `lock` を消す。前回が落ちて `lock` が残っていた場合は、中のプロセスの番号が動いていなければ古い印として消し、作り直す。

## 3. 時計

### 3.1 数える範囲

ゲームの経過時間は、準備の完了（BD01 6.2、最初の手番の開始）から数え、一時停止の間を除く。

### 3.2 単調時計

経過は `process.hrtime.bigint()`（単調時計）で数える。PCの時刻が NTP の同期や手動の変更で動いても、単調時計は影響を受けない。

壁時計（`Date`）は、記録の `at` と画面の時刻表示にだけ使う。

PCがスリープしている間に単調時計が進むかは、Windows では確かめていない（未検証）。どちらの場合も破綻しないように、次の検出を入れる。

- 時計は1秒ごとに単調時計を読む。前回との差が5秒を超えたら、PCが止まっていたとみなす。
- その場合、止まっていた分を経過に含めず、ゲームを一時停止（`pause`）にして、大画面に「時計が止まっていたため一時停止しました」と出す。再開はホストが押す。

### 3.3 控えと再起動

時計は10秒ごとに、その時点の経過を `clock.json` に書く。

再起動したときの経過は、`clock.json` の値と、記録の最後の行の `elapsedMs` の大きい方とする。サーバーが止まっていた間は経過に含めない。止まっている間は誰も操作できず、遊んでいないのと同じだからである。

再起動したゲームは、エンジンにも一時停止を記録してから始める（2.7の手順7）。

### 3.4 markTimeUp と一時停止を出す時機

- 経過が `timeLimitMinutes`（70分）に達した最初の1秒ごとの読み取りで、サーバーは `markTimeUp(at)` をキューに入れる。`at` は経過のミリ秒である。
- ホストが大画面で一時停止を押すと、サーバーは `pause(at)` をキューに入れ、時計を止める。再開で `resume(at)` を入れ、時計を進める。
- 一時停止の間に70分に達することはない。時計が止まっているためである。

`markTimeUp` も記録に残るため、再適用すれば同じ時点で同じ終わり方になる（方式設計5.9）。

## 4. 起動と運用

### 4.1 前提

| 項目 | 内容 |
|---|---|
| PC | 会社の Windows 11 のノートPC。Node.js 24 が入っている（2026-10-26 に確認） |
| ポート | 8787（環境変数 `PORT` で変えられる）。待ち受けは全アドレス（`0.0.0.0`） |
| 画面のファイル | `npm run build` で作った静的ファイルを、サーバーが配る。開発用のサーバー（Vite）は使わない |

### 4.2 社内規程で未確定の点

次の3点は、社内規程の確認が済んでいない。許可が得られない場合、この章の手順は使えず、別の構成（私物のPC、持ち込みのルーター）を検討する必要がある。

1. 会社のPCで、LANからの接続を受けるサーバーを起動してよいか。
2. Windows のファイアウォールに、受信を許可する規則を足してよいか。会社のPCでは、管理者の権限が要る場合や、グループポリシーで禁止されている場合がある。
3. モバイルホットスポットを使ってよいか。グループポリシーで「インターネット接続の共有」が禁止されていると、ホットスポットを有効にできない場合がある（未検証）。

### 4.3 初回の準備

1. リポジトリの `app/` で `npm ci` と `npm run build` を実行する。
2. ファイアウォールの許可を作る。初回の起動で Windows が許可の画面を出した場合は「プライベート ネットワーク」に許可を与える。画面が出ない場合や、管理者の権限が要る場合は、管理者の PowerShell で次を実行する（4.2の2の許可が前提）。

   ```powershell
   New-NetFirewallRule -DisplayName "WORD FARM" -Direction Inbound -Protocol TCP -LocalPort 8787 -Action Allow -Profile Private
   ```

3. ホットスポットの接続先に Windows が付けるネットワークの種類（プライベートかパブリックか）を確かめる（未検証）。パブリックの場合は、上の規則の `-Profile` に `Public` も足す必要がある。パブリックの許可は、ほかの場所でも受信を許すことになるため、遊ぶときだけ規則を有効にする運用にする。
4. 電源の設定を変える。電源につないだときのスリープを「なし」にし、蓋を閉じたときの動作を「何もしない」にする。ホストもスマホで遊ぶため、ホストPCは長い間操作されない。スリープに入ると、ホットスポットも止まり、全員の接続が切れる。

ホストPCの画面の消灯と画面のロックには、大画面ビューで画面の消灯を防ぐ機能（Screen Wake Lock）を取って備える。`http://localhost` は安全なコンテキストとして扱われるため、大画面ビューではこの機能を使える見込みである（未検証）。

会社のPCでは、一定時間操作がないと画面をロックする設定が、グループポリシーで強制されていることがある。この強制を Screen Wake Lock で止められるかは確かめていない（未検証）。止められない場合は、遊ぶ間はホストが時々PCを操作する運用にする。4.9の実測で確かめる。

### 4.4 遊ぶ日の手順

1. ホットスポットを有効にする。設定の「ネットワークとインターネット」から「モバイル ホットスポット」を開き、共有元の接続を選んで有効にする。古いスマホのために、帯域は 2.4GHz を選ぶ。共有元の接続がないと有効にできない場合がある（方式設計13章、未検証）。
2. `app/` で `npm start` を実行する。サーバーは、使えるアドレスとポートを表示し、既定のブラウザで大画面ビュー（`http://localhost:8787/board`）を開く。
3. 大画面ビューを全画面にし、HDMI でテレビかプロジェクターに映す。管理者でない PowerShell で `powercfg /requests` を実行し、ブラウザが画面の消灯を止める要求（DISPLAY の欄）を出していることを確かめる。
4. 大画面に出るQRコードのアドレスが、ホットスポットのアドレス（既定は `192.168.137.1`、未検証）になっているかを確かめる。違う場合は、大画面のアドレスの一覧から選び直す（4.5）。
5. 参加者がQRコードを読み、名前を入れて参加する。
6. ホストが大画面で参加者を時計回りに並べ、上級者の倍率（BD01 8.4）を設定して、ゲームを始める。

### 4.5 アドレスの選び方

サーバーは、`os.networkInterfaces()` から、IPv4 で、ループバックでないアドレスを集める。

既定の候補は次の順で選ぶ。

1. `192.168.137.1`（ホットスポットの既定。あれば最優先）
2. 名前に `Wi-Fi` か `Ethernet` を含むネットワークのアドレス
3. それ以外

名前に `vEthernet`、`VirtualBox`、`VMware`、`WSL` を含むものは、仮想のネットワークとして候補の後ろに回す。スマホから届かないためである。

ホストは大画面で候補を切り替えられる。選んだアドレスはQRコードに入れ、`seats.json` には保存しない。再起動でネットワークが変わることがあるためである。

### 4.6 QRコード

| 用途 | 入れるURL |
|---|---|
| 参加 | `http://<アドレス>:8787/p?room=<部屋のコード>` |
| 席の作り直し（方式設計7.4の手順4） | `http://<アドレス>:8787/p?room=<部屋のコード>&claim=<使い捨ての合言葉>` |

使い捨ての合言葉は、ホストが席の作り直しを押すたびに作り、1回使われるか5分たつと無効にする。

席の作り直しのQRコードは、ホストPCの画面の小窓に出し、HDMI の先の大画面には出さない。合言葉で入った端末には、どの席かを確かめさせ、ホストが大画面で承認してから、その席の新しいトークンを発行し、古いトークンを無効にする（BD03 3.6）。テレビに映ったQRコードを別の参加者が先に読んで、他人の席に入ることを防ぐためである。

QRコードの画像はサーバーが作る（例：`qrcode` パッケージ）。外部のサービスは使わない。インターネットにつながらない環境で遊ぶためである。

### 4.7 終わり方と後片付け

1. ゲームが終わると、サーバーは記録を書き出す（5章）。ホストは大画面で書き出しの完了を確かめる。
2. サーバーを止める（ターミナルで Ctrl+C）。サーバーは新しい要求を受け付けるのをやめ、キューを処理し終え、`clock.json` を書いてから終わる。
3. ホットスポットを無効にする。
4. 遊ぶときだけ有効にしたファイアウォールの規則を無効にする（4.3の3）。
5. 記録の書き出し（`export/`）のうち、名前を伏せたもの（5.3）だけをリポジトリの `sim/results/` などに移す。

### 4.8 障害の時の対処

| 事象 | まず確かめること | 対処 |
|---|---|---|
| スマホがつながらない | スマホがホットスポットにつながっているか。QRコードのアドレスが合っているか | アドレスを選び直す（4.5）。ファイアウォールの許可を確かめる（4.3） |
| 一部のスマホだけつながらない | Android がモバイル通信に切り替えていないか（方式設計11.5、未検証） | スマホのモバイルデータを一時的に切る |
| サーバーが落ちた | ターミナルの表示、`server.log` | `npm start` で再起動する。2.7の手順で自動的に戻る。ホストが大画面で再開を押す |
| 再起動で拒否か照合の不一致が出た | 大画面の表示（2.7） | 記録を作ったエンジンの版に戻して再起動する（2.7）。戻せない場合は、紙で続きを遊ぶ |
| スマホをなくした、電池が切れた | ほかの端末を用意できるか | 管理操作で席を作り直し、席専用のQRコードを別の端末で読む（4.6） |
| 時計がずれた、止まった | 大画面の経過時間 | PCが止まっていた場合は自動で一時停止している（3.2）。ホストが再開を押す。経過がおかしい場合は、70分の打ち切りを使わず、ホストが `abortGame` で終える |
| 保存の異常が出た | ディスクの空き、ファイルの権限 | 遊ぶのをやめ、記録を控える。保存できない状態で続けると、落ちたときに戻せない（2.5） |
| 起動すると「別のサーバーが動いています」と出る | ほかのターミナルで `npm start` が動いていないか | 動いていれば、そちらを使う。動いていなければ `app/data/lock` を消して起動し直す（2.10） |
| 大画面がロック画面になった、PCがスリープした | 電源の設定（4.3の手順4） | ロックを解除する。スリープから戻った場合は、時計が自動で一時停止している（3.2）。ホストが再開を押す |

### 4.9 M0 の前に行う実測

ネットワークと会社のPCの制約は、構成を決める前提である。開発の M0 より前に、エンジンも画面もない小さな試しで確かめる。社内規程の確認（4.2）と同じ時期に行う。

試しに使うのは、静的なページ1枚と、それを配る数十行の Node のサーバーである。ページには、WebSocket の往復、無音の動画の繰り返し再生（消灯を防ぐ方法）、`crypto.getRandomValues` の呼び出しを入れる。サーバーは `0.0.0.0:8787` で待ち受ける。

| 確かめること | 方法 | 関係する箇所 |
|---|---|---|
| ホットスポットを有効にできるか。共有元の接続なしで有効にできるか | 会社のPCで有効にしてみる。社内のネットワークを外した状態でも試す | 方式設計13章、4.2 |
| ホットスポットのアドレス | `ipconfig` で、ホットスポットのアダプタのアドレスを見る（既定は `192.168.137.1` の見込み） | 4.5 |
| ネットワークの種類 | `Get-NetConnectionProfile` で、ホットスポットとその他の接続がプライベートかパブリックかを見る | 4.3の手順3 |
| スマホから届くか | iPhone と Android をホットスポットにつなぎ、QRコードからページを開く | 4.4 |
| HTTP の警告 | Chrome と Safari で、LAN のアドレスへの HTTP で警告の画面が出るか | 方式設計2.1 |
| スマホの消灯 | ページを開いたまま5分置き、無音の動画で消灯を防げるか | 方式設計2.1 |
| Android のモバイル通信への切り替え | モバイルデータを入れたまま、インターネットにつながらないホットスポットでページが開けるか | 方式設計13章 |
| fsync の時間 | Node で `appendFile` と `fsync` を1000回繰り返し、50%点と95%点を測る | 6章 |
| スリープの間の単調時計 | 1秒ごとに `process.hrtime` と `Date` を記録しながら、PCを1分スリープさせ、両者の差を見る | 3.2 |
| 画面のロック | 大画面のページで Screen Wake Lock を取り、無操作で30分置いて、ロックされるかを見る | 4.3の手順4 |

結果は本書の該当箇所に書き戻し、「未検証」を外す。構成を変える必要が出た場合（ホットスポットが使えない等）は、方式設計に戻って判断する。

## 5. 記録の書き出し

### 5.1 書き出すファイル

ゲームが終わったとき（出来事 `gameOver`）と、ホストが管理操作 `exportRecord` で求めたときに、`export/` に次を書く。集計に使う出来事は、記録の有効な行を先頭から再適用して作る。取り消された行の出来事は、再適用しないため含まれない。

| ファイル | 内容 |
|---|---|
| `summary.json` | 1局の概要（5.2の末尾）。名前を入れた `summary_named.json` と、名前を伏せた `summary.json` の2つ |
| `turns.csv` | 手番ごとの1行 |
| `points.csv` | 点を得た出来事ごとの1行 |
| `actions.csv` | 行動、銀行、交換、日本語の支払いの出来事ごとの1行 |
| `orders.csv` | 注文と共同注文ごとの1行 |

### 5.2 列の定義

`turns.csv`

| 列 | 内容 |
|---|---|
| `turn` | 手番の通し番号 |
| `round` | ラウンド |
| `seat` | 席 |
| `player` | 5.3の表示名 |
| `dice` | 出目の合計 |
| `startMs`、`endMs`、`durationMs` | 経過時間で表した手番の始まり、終わり、長さ（一時停止を除く） |
| `actions` | この手番の行動の数 |
| `trades` | 成立した交換の数 |
| `japanese` | 日本語の支払いの数（全員分） |
| `hpAfter` | 手番の終わりの、手番の人の点（半点） |

`points.csv`

| 列 | 内容 |
|---|---|
| `turn`、`seat`、`player` | いつ、誰が |
| `src` | `order`、`bonus`、`jointRow`、`jointFinish`、`jointHalf`（BD01 2.3） |
| `orderId`、`level` | 対象の注文と難易度 |
| `hp`、`coins` | 得た点（半点）とコイン |

`actions.csv`

| 列 | 内容 |
|---|---|
| `turn`、`elapsedMs`、`seat`、`player` | いつ、誰が |
| `event` | 出来事の名前 |
| `detail` | 中身の要約（例 `carrot×3`、`word/coin`、`harbor:seed 2→1 wheat`） |
| `sentence` | 宣言の英文（ある場合） |

`orders.csv`

| 列 | 内容 |
|---|---|
| `orderId`、`kind`、`level` | 注文の識別子、通常か共同、難易度 |
| `text` | 英文 |
| `revealedTurn`、`resolvedTurn` | 表になった手番、片付いた手番 |
| `outcome` | `succeeded`、`expired`、`completed`、`unrevealed`、`openAtEnd` |
| `failedAttempts` | 不成立の回数 |
| `seat` | 達成した人（ある場合） |

`summary.json` には、開始と終了の日時、経過時間、人数、終わり方、順位、手番の数、ラウンドの数、ルールの版、エンジンの版を入れる。

設計メモ5章の項目との対応は次のとおり。方式設計10章の表を、ファイルと列に割り当てたものである。

| 5章の項目 | 書き出し |
|---|---|
| 1 所要時間 | `summary.json` の経過時間。`turns.csv` の `durationMs` |
| 3 日本語の支払い | `actions.csv` の `japanesePaid` |
| 4 共同注文 | `orders.csv` の共同注文の `outcome`。`points.csv` の `jointHalf` |
| 5 点の出どころ | `points.csv` |
| 6 産物の購入 | `actions.csv` の `productBought` |
| 7 港、拠点の追加、交換 | `actions.csv` の `harborTraded`、`houseBuilt`、`tradeAccepted` |
| 9 読み違え | `orders.csv` の `failedAttempts`。`actions.csv` の `orderFailed` |
| 11 ボーナス注文 | `points.csv` の `src` が `bonus` の行 |
| 12 動物の売却 | `actions.csv` の `animalSold` |
| 13 時間切れの注文 | `orders.csv` の `outcome` が `expired` の行 |
| 14 席ごとの順位 | `summary.json` の順位 |
| 15 終わり方 | `summary.json` の終わり方 |

5章の項目のうち、2、8、10、16 は数えられないため、観察シートで記録する（方式設計10章）。8（Market の周りの拠点）は、拠点の位置から求められるが、MVP では書き出さない。

### 5.3 名前の扱い

参加者の名前は、社内の人の名前であることが多い。リポジトリに入れる記録には名前を残さない。

- `export/` には、名前を入れたもの（`*_named.csv`）と、名前を `P0`〜`P3`（席の番号）に置き換えたもの（`*.csv`）の2組を書く。
- リポジトリに移してよいのは、名前を置き換えた組だけとする（4.7の手順5）。
- `commands.jsonl` には名前を書かず、席の番号だけを書く。名前は `seats.json` だけに置く。
- エンジンの状態（`GameState`）にも名前を持たせない（2.6）。ゲームの作成（`createGame`）の行にも、名前ではなく `participantId` を書く。照合の行のハッシュ（2.4）にも名前は入らない。
- `summary.json` も、名前を入れたもの（`summary_named.json`）と伏せたもの（`summary.json`）の2つを書く。順位に名前が入ったものを、誤ってリポジトリに移さないためである。

## 6. 非機能の目標

| 項目 | 目標 | 根拠と確かめ方 |
|---|---|---|
| 応答時間 | スマホでボタンを押してから、全端末の表示が変わるまで、95%が300ミリ秒以内 | 対面で遊ぶため、人が遅れを感じない範囲。M5 の実機のテストで測る（未検証） |
| fsync の時間 | 1件あたり50ミリ秒以内 | 会社のPCのSSDで測る（未検証。4.9）。超える場合は、手順1.2の4と6の順を見直す |
| 同時接続 | 16本まで | プレイヤー4、大画面と予備の閲覧が数本。この数で WebSocket の負荷は問題にならない見込み |
| 1局の記録の大きさ | `commands.jsonl` 1MB 以内 | 1局を約50手番、500〜1000件のコマンドと見積もった（BD03 4章と同じ見積もり。未検証。M1 で、模擬の出来事の数から実測する） |
| 復旧の時間 | 再起動から再開できるまで10秒以内 | 全件の再適用を含む。M3 で測る（未検証） |

### 6.1 動作の記録（server.log）

`server.log` には、起動と終了、接続と切断、拒否、保存の異常、時計の異常を、1行1件で書く。手札の中身や注文の条件など、秘密の情報は書かない。

1局で1MBを超えない量に抑える。1つの `view` の送信のような頻繁な処理は書かない。
