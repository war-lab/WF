# 基本設計 BD05 サーバー、保存、運用

更新日：2026-10-27

位置づけ：Cloudflare で動かすサーバー（`app/packages/worker`）の内部構成、保存の形式、時計、デプロイと運用の手順、記録の書き出し、非機能の目標を定める。

上位の方針は `WORD_FARM_APP_DESIGN_v0.1.md`（以下、方式設計）の3章、7章、8章、10章を正とする。エンジンの型とコマンドは BD01、注文と乱数は BD02 を正とする。

## 結論

サーバーは Cloudflare Workers と Durable Objects の無料プランで動かす。有料プランには上げず、支払いの手段も登録しない。無料プランの上限を超えると処理がエラーになるだけで、課金はされない（4.2）。

部屋1つを Durable Object 1つとする。Durable Object は、同じ識別子に対して世界で1つしか動かず、届いた要求を1つずつ処理する。この性質で、旧設計（ホストPCの Node.js）のキュー、ロックファイル、二重起動の防止が要らなくなる。

保存は Durable Object の SQLite に行う。受け付けたコマンドを1行とし、同じ行に適用後の状態の写し（スナップショット）を持たせる。再開と取り消しは、写しを読んで行い、記録の先頭からの再適用はしない。再開を1行の読み込みで済ませ、1件の処理の時間を局の長さによらず短く保つためである（1.4）。

端末への `ack` は、記録の書き込みが確定してから届く。Durable Object は、書き込みが確定するまで外への送信を止める（出力ゲート）。書き込みに失敗した場合は、Durable Object が作り直され、止めていた送信は捨てられる。端末は再接続して同じ `id` で送り直す（2.5）。

管理操作は、ホストの鍵（Worker の秘密の値）を知る大画面だけに許す。旧設計の「ループバックからの接続だけ」は、サーバーがホストPCの外にあるため使えない（1.2）。

ゲームの時計は、サーバーの時刻から、準備の完了の時刻と一時停止の合計を引いて求め、大画面に出すだけとする。70分の打ち切りは自動にせず、ホストが「最終ラウンドにする」を押す（3章、方式設計5.9）。

記録の書き出しは、ゲームの終わりのあとに、大画面のブラウザが記録を取り出し、ブラウザの中でエンジンを再適用して作る（5章）。再適用をサーバーで行わないのは、Durable Object の1件の処理を短く保つためである（1.4）。

## 1. 内部構成

### 1.1 部品

| 部品 | 置き場所 | 役割 |
|---|---|---|
| 入口の Worker | Worker | 画面の静的ファイルを配る（Workers Static Assets）。部屋の作成、記録の取り出し（HTTP の API）。WebSocket の接続を、部屋の ID から対応する Durable Object へ渡す |
| 部屋 | Durable Object | 参加者、席、ゲームの状態、`rev` を持つ。1つの部屋に1つ |
| 接続の管理 | Durable Object | WebSocket の接続と参加者の対応を持つ。休止できる WebSocket（WebSocket Hibernation API）を使う。1つの席には最後につないだ1本だけを有効にする |
| エンジン | Durable Object | BD01 の `createGame`、`apply`、`viewFor`、`legalActions` を呼ぶ |
| 保存 | Durable Object | SQLite への記録の追記と、状態の写しの保存（2章） |
| 時計 | Durable Object | ゲームの経過を求め、`view` に付ける（3章） |
| 管理の門番 | Worker と Durable Object | 部屋の作成、管理操作、記録の取り出し、部屋の削除を、ホストの鍵を示した要求に限る（1.2） |

部屋の処理の本体は `app/packages/worker/src/room.ts` に置き、保存（SQL）、接続、時刻、乱数、ハッシュを外から受け取る形にした。Durable Object（`index.ts`）は、Cloudflare の API をこの形に合わせて渡すだけである。同じコードを、Node.js の `node:sqlite` と偽の接続で単体テストするためである（BD06 6章）。

Durable Object の名前は部屋の ID から作る（`idFromName(roomId)`）。部屋の ID は、部屋の作成時に Worker が `crypto.getRandomValues` で作る128ビットの値の16進表記（32文字）とする。推測できない値にするのは、部屋のURLを知らない人が参加の画面を開けないようにするためである。

休止できる WebSocket を使うのは、何も届かない間、Durable Object を止めておくためである。止まっている間は時間の課金の対象にならず、無料の枠（4.2）を減らさない。Durable Object は、10秒間、要求も出来事も届かないと休止に入る（Cloudflare の資料）。遊んでいる間は、端末5台が10秒ごとに生存確認（BD03 3.7）を送るため、ほとんど休止しない。休止するのは、一時停止の間や、全員の接続が切れた間などである。

休止から戻ると、メモリ上の状態は消えている。Durable Object は、次の要求を処理する前に SQLite から状態を読み直す（2.7）。

### 1.2 ホストの鍵と管理の門番

**ホストの鍵** は、Worker の秘密の値（`HOST_KEY`、`wrangler secret put` で設定）に置く長い乱数の文字列である。開発者が作り、ホストに渡す。

ホストの鍵を示した要求だけに、次を許す。

- 部屋の作成（`POST /api/rooms`）
- 管理操作（WebSocket の `admin` のメッセージ）
- 記録の取り出しと部屋の削除（5章、2.11）

大画面ビューは、初回にホストの鍵を入れさせ、`localStorage` に保存する。接続のたびに `hello` で鍵を送り、Durable Object は鍵が合う接続にだけ管理を許す（`welcome` の `admin: true`）。鍵のない大画面ビューは閲覧だけができる。参加者のスマホで大画面のURLを開いても、管理操作はできない。

実装では次の3点を守る。

- 鍵の比較は、長さによらず一定の時間で行う。比較の時間の違いから鍵を推測されないためである。
- 鍵はURLに入れない。URLは閲覧の履歴やQRコードを通じて他人に見えるためである。HTTP の API ではヘッダ（`Authorization: Bearer <鍵>`）で送る。
- 鍵を記録とログに書かない。

鍵が漏れた場合は、`wrangler secret put HOST_KEY` で新しい鍵に替える。替えると、保存した鍵を持つ大画面は管理を失い、新しい鍵を入れ直す必要がある。

旧設計の `Origin` の確かめは要らなくなる。乗っ取りの攻撃は、ブラウザが自動で付ける認証の情報（クッキーや接続元のアドレス）を悪用するもので、鍵をメッセージの中で明示して送る方式には効かないためである。

### 1.3 コマンドの処理の順番

Durable Object は、届いたメッセージを1つずつ処理する。コマンドの処理では、SQLite の操作を同期の API（`ctx.storage.sql.exec`）で行い、途中で `await` しない。途中で待たなければ、次のメッセージの処理が割り込むことはなく、旧設計のキューは要らない。

`hello` の処理だけは、トークンのハッシュ（`crypto.subtle.digest`）を求めるために `await` を挟む。待っている間に別のメッセージが割り込みうるため、`await` のあとで参加者と接続の状態を読み直してから、席の割り当てと `replaced`（BD03 3.6）を判定する。

1つのコマンドの処理は次の順で行う。

1. 形を zod で確かめる。合わなければ `reject`（`BAD_MESSAGE`）を返す。
2. 一時停止中なら、プレイヤーのコマンドに `reject`（`PAUSED`）を返して終える（3.3）。管理操作は受け付ける。
3. `id` が処理済みかを確かめる。記録の表を `id` で引き（索引を張る）、あれば前回の `ack` を返して終える。メモリ上の拒否の表にあれば、前回の `reject` を返して終える。
4. エンジンの `apply` を呼ぶ。拒否なら `reject` を返し、メモリ上の拒否の表に入れて終える。拒否は記録に追記しない。
5. 受け付けたなら、`rev` を1増やし、記録の1行（2.3）を、適用後の状態の写しと併せて1つのトランザクション（`ctx.storage.transactionSync`）で書く。
6. メモリ上の状態を新しいものに置き換える。
7. `ack` を送り主に返す。
8. 接続しているすべての端末へ、その端末向けの `view` と出来事を送る。

手順7と8の送信は、手順5の書き込みが確定するまで、Durable Object の出力ゲートで止められる見込みである。WebSocket の送信が止められるかは推論で、M3 で確かめる（2.5）。

手順4で状態を変えずに判定できるのは、エンジンが純粋な関数だからである。判定の前に記録すると、拒否されたコマンドまで記録に残る。

拒否の表は、メモリにだけ持つ。休止や作り直しで消えるが、拒否されたコマンドを送り直された場合は、その時点の状態で判定し直すだけで、二重の適用は起きない。

手順1の `BAD_MESSAGE` は、`cmd` の中のコマンドの形が誤っている場合の返し方である。`cmd` 以外のメッセージの形の誤りには `error` を返す（BD03 3.8）。

### 1.4 無料プランの CPU の上限

Workers の料金の資料は、無料プランで1回の要求に使える CPU 時間を 10 ミリ秒としている。Durable Object の資料は、1回の処理（HTTP の要求、WebSocket のメッセージ1件、Alarm）ごとの上限の既定を30秒としている。無料プランの Durable Object にどちらが適用されるかは、資料に書かれていない。

2026-10-27 の試作（4.9）では、無料プランの Durable Object が1件の HTTP の要求で CPU 時間を約1.6秒使っても、エラーにならなかった（Cloudflare の分析のデータで確かめた）。Worker も、約126ミリ秒でエラーにならなかった。このため、1件の処理が 10 ミリ秒で打ち切られることはない、と判断する。

ただし、確かめたのは数十件の要求で、上限を超える処理を続けた場合に制限が厳しくなるかは確かめていない（未検証）。資料の 10 ミリ秒の記述も残っている。そのため、1件の処理を数ミリ秒に収める方針は目安として残す。開発者の別のアプリ（同じアカウントの `beb-party`）の Durable Object は、実際のプレイで1件の CPU 時間が50%点で約1.1ミリ秒、99.9%点で約6.2ミリ秒だった。

| 処理 | 1件で行うこと | 方針 |
|---|---|---|
| コマンド | `apply`、状態の写しの書き込み、5台分の `viewFor` と JSON への変換 | M1 で、Node.js で1件の時間を測る。目安は5ミリ秒以内（6章） |
| 取り消し | 写しの読み込み | 先頭からの再適用をしない（2.9） |
| 再開 | 最後の行の写しの読み込み | 同上（2.7） |
| ゲームの作成 | タイルの配置のやり直し、注文の生成 | Durable Object で行う。M1 で時間を測る |
| 記録の書き出し | 全件の再適用 | サーバーで行わず、大画面のブラウザで行う（5章） |

## 2. 保存

### 2.1 表の構成

1つの部屋の Durable Object は、次の4つの表を SQLite に持つ。

| 表 | 内容 | 書く時機 |
|---|---|---|
| `meta` | ゲームの前提（2.2） | 部屋の作成時と、ゲームの作成時 |
| `participants` | 参加者、席、トークンのハッシュ（2.6） | ロビーの変更、席の再発行のたび |
| `commands` | 受け付けたコマンド、取り消し、その時点の状態の写し（2.3、2.4） | コマンドを受け付けるたび |
| `room` | `rev`、時計（3章）、部屋の段階（ロビー、ゲーム中、終わり） | 変わるたび |

表は1行ずつ書き、まとめて書き換える操作はしない。

### 2.2 meta

ゲームの作成時に1回だけ書き、以後は書き換えない。

```json
{
  "format": 1,
  "roomId": "8b1f0c2e9d4a7b3e5f6c1d0a2b9e8f7c",
  "createdAt": "2026-11-05T18:30:12.345+09:00",
  "engineVersion": "0.1.0+e3b0c442",
  "rulesVersion": "0.9",
  "config": { "...": "BD01 3章のルール設定。既定値から変えた項目も含めた全量" },
  "seed": "9f1c0a7b3e5d4c2a8b6e1f0d9c7a5b3e",
  "n": 4
}
```

`engineVersion` は、エンジンのパッケージの版と、エンジンのソース（`app/packages/engine/src` の全ファイル）から求めたハッシュの先頭8文字を並べたものである。`app/packages/worker/scripts/engine-version.mjs` が `wrangler dev`、`wrangler deploy`、テストの前に求め、`src/engine-version.ts` に書く。改行の違い（CRLF と LF）では変わらないようにそろえてから求める。今のエンジンと記録を作ったエンジンが違うことを検出するために使う（2.10）。

git のコミットの番号を使わないのは、画面の文言だけを直したデプロイでも、遊んでいる部屋が止まってしまうためである。エンジンのソースから求めれば、エンジンを変えないデプロイでは部屋は止まらない。

`seed` は、ゲームの再現に要る。ゲームが終わるまで、Durable Object の外に出さない。ゲームの途中に知られると、伏せた注文の山の順番を計算で求められてしまうためである。記録の取り出し（5.1）も、ゲームが終わるまで許さない。

### 2.3 commands

受け付けたコマンド1件を1行とする。行は追記するだけで、書き換えも削除もしない（部屋の削除を除く。2.11）。

| 列 | 内容 |
|---|---|
| `seq` | 記録の行の通し番号。1から始まり、取り消しの行も含めて1ずつ増える。主キー |
| `rev` | この行を適用したあとの `rev`（2.8） |
| `at` | 時刻（ISO 8601）。記録の読みやすさのためで、再適用には使わない |
| `elapsedMs` | ゲームの経過時間（3章）。手番の時間の集計に使う |
| `id` | コマンドの一意の値。128ビットの16進表記（32文字）。一意の索引を張る。サーバーが発したコマンドも同じ形で、出どころは `actor` で区別する（BD03 3.2） |
| `actor` | `{"k":"seat","seat":n}`、`{"k":"admin"}`、`{"k":"server"}` のどれか（JSON）。`server` はゲームの作成の行だけに使う |
| `cmd` | BD01 のコマンド（JSON）。ゲームの作成（`createGame`）も1行目のコマンドとして残す |
| `meta` | 記録だけに残す付随の情報（JSON）。例 `{"sentenceShown":false}` |
| `undo` | 取り消しの行だけに入れる。この取り消しで無効にした行の `seq` の一覧（JSON） |
| `state` | この行を適用したあとの `GameState` の写し（JSON。2.4） |

取り消しの行の `undo` の例は `{"seqs":[63]}` である。取り消しは最後の有効な行を1つずつ行うため（2.9）、並ぶのは常に1行である。形を一覧にしておくのは、記録の読み手が取り消しの行をほかの行と同じ手順で扱えるようにするためである。

一時停止と再開はエンジンのコマンドではないため、`commands` に行を作らない（3.3）。

### 2.4 状態の写し

各行の `state` には、その行を適用したあとのゲームの状態を全量で入れる。状態は数KB〜20KB の見込みで（BD03 4章の見積もりから推定。未検証）、1行の上限（2MB）に収まる。

写しを全行に持たせるのは、次の2つの処理で、先頭からの再適用を避けるためである。

- 再開：最後の行の写しを読めば、今の状態になる（2.7）。
- 取り消し：取り消す行の直前の有効な行の写しを読めば、取り消したあとの状態になる（2.9）。

旧設計では写しを持たず、照合の行（手番の終わりの状態のハッシュ）で再適用の結果を確かめていた。新しい設計では、写しがその役目を兼ねる。開発の道具（5.4）で記録を先頭から再適用し、各行の写しと比べれば、エンジンの判定が記録の時と同じかを確かめられる。

参加者の名前は `GameState` に入らないため（5.3）、写しにも名前は入らない。

出来事の記録は保存しない。出来事は記録の再適用で作り直せるため、記録の書き出し（5章）の際に、ブラウザで再適用して作る。出来事の名前は次の39個とする。中身の項目と通し番号（`eventSeq`）は BD03 で定める。

gameCreated, seatsAssigned, housePlaced, cardsGranted, promptsOpened, promptAnswered, diceRolled, cardsDiscarded, harvested, planted, animalBought, fed, productsSold, animalSold, orderDeclared, orderSucceeded, orderFailed, ordersRevealed, orderExpired, jointRowFilled, jointCompleted, jointExpired, houseBuilt, bankTraded, harborTraded, cardBought, productBought, tradeProposed, tradeAccepted, tradeDeclined, tradeWithdrawn, japanesePaid, turnStarted, turnEnded, endFlagged, paused, resumed, gameOver, undone

`undone`、`paused`、`resumed` の3つは、エンジンではなくサーバーが出す（2.9、3.3）。この3つは記録の再適用では作られないため、書き出しには含まれない。

### 2.5 書き込みに失敗したとき

Cloudflare の資料では、書き込みが確定するまで Durable Object からの外への送信（HTTP の応答と `fetch`）は止められ、書き込みに失敗した場合は、Durable Object が作り直され、止めていた送信は捨てられる。資料は WebSocket の送信を名指ししていない。WebSocket の送信も同じく止められるという前提は推論で（未検証）、M3 で確かめる（4.9）。

この性質から、次のことが成り立つ。

- 書き込みが確定しなかったコマンドの `ack` は、端末に届かない。端末は、`ack` の届いていないコマンドを、再接続のあとに同じ `id` で送り直す（BD03 3.5）。
- 作り直された Durable Object は、SQLite から状態を読み直す（2.7）。失敗した書き込みが記録に残っていなければ、送り直しは新しいコマンドとして判定される。残っていれば、`id` の索引で処理済みと分かり、前回の `ack` を返す。どちらの場合も二重に適用されない。

失敗した書き込みが記録に残るか消えるかは、資料に書かれていない（未検証）。上の手順は、どちらの場合でも正しく動くように作る。

2026-11-06 に Miniflare（手元の Workers の実行環境）で、書き込みの直後に `ctx.abort()` で作り直させたところ、書き込みは残らず、`ack` も届かなかった。同じ `id` の送り直しは新しいコマンドとして1回だけ適用された（BD06 TC-SRV-20）。Cloudflare の本番で同じになるかは確かめていない（未検証。DEV-18 で確かめる）。

WebSocket の送信が止められなかった場合は、確定していない `ack` が端末に届くことがある。その直後に作り直しが起きると、端末は受け付けられたと表示したのに、コマンドが記録にない状態になる。端末は再接続のあとに `view` を受け取り直すため、画面は記録どおりに戻り、失われた操作は本人がやり直す。起きるのは、書き込みが失敗したときに限られる。

旧設計の、書き込み前の長さまでの切り詰めと、以後のコマンドの拒否（fail-stop）は要らなくなる。1行の書き込みが1つのトランザクションで、途中まで書けた行が残らないためである。

保存の容量の上限（無料プランで全体 5GB）に達した場合は、書き込みが `SQLITE_FULL` で失敗する。1局の記録は数十MBまでの見込みで（6章）、終わった部屋を消していけば達しない（2.11）。

Durable Object の無料の上限（要求の数など）に達した場合のエラーの番号は、資料に書かれていない。大画面とスマホは、Durable Object への要求が失敗したことを受け取ったら、「サーバーの上限に達した可能性があります」と出す（4.8）。

### 2.6 participants

部屋の参加者、席、トークンを持つ。

| 列 | 内容 |
|---|---|
| `participantId` | 参加者の識別子（例 `p1`） |
| `name` | 名前（1〜12文字） |
| `order` | ロビーでの時計回りの並び |
| `seat` | ゲームの作成後の席。ロビーの間は空 |
| `color` | 色 |
| `japaneseRate` | 上級者の倍率（1 か 2） |
| `tokenHash` | トークンの SHA-256 のハッシュ |

トークンはハッシュだけを保存する。保存の中身を見ただけでは、他人の席に入れないようにするためである。トークンそのものは、発行の時にスマホへ1回だけ送る。

参加者の名前は、この表とロビーの状態にだけ置く。エンジンの状態（`GameState`）は `participantId` だけを持ち、名前は持たない。名前は、Durable Object が `view` を作るときに付ける（BD03 1.3）。

名前は Cloudflare の保存に残る。社内の人の本名を外部のサービスに置かないよう、参加画面で「あだ名で入ってください」と促す（BD04）。

### 2.7 読み込み（作り直しと休止からの復帰）

Durable Object は、作り直されたときと休止から戻ったときに、メモリ上の状態を失う。次のメッセージか HTTP の要求を処理する前に、コンストラクタで次の手順を行う（`ctx.blockConcurrencyWhile` の中で行い、読み込みの途中に要求が割り込まないようにする）。

1. `room` の表があるかを `sqlite_master` で調べる。なければ初期化されていない部屋とし、何も書かずに終える（2.11）。
2. `meta`、`room`、`participants` を読む。
3. `meta` があれば、2.10 の版の確認を行う。版が違えば、止めた印をメモリに持つ。例外は投げない。コンストラクタで例外を投げると Durable Object が作り直され、確認を繰り返すためである。
4. `commands` の最後の行の `state` を読み、今の状態とする。
5. `rev` を `room` から読む。

先頭からの再適用はしない（1.4）。処理済みの `id` は、メモリに持たず、`commands` の索引で引く（1.3の手順3）。

休止からの復帰では、接続は切れていない。各接続には、休止の間も残る付箋（`serializeAttachment`、上限16KB）で、参加者の識別子と、管理を許したかを持たせる。復帰のあと、Durable Object は `ctx.getWebSockets()` で接続の一覧と付箋を読み直す。

接続ごとの「最後に受け取った時刻」（BD03 3.7）はメモリにだけ持つ。休止から戻ったときは、すべての接続の時刻を戻った時点とみなす。付箋や SQLite に持つと、生存確認のたびに書き込みが増えるためである。この扱いで、死んだ接続が切られるのは、戻ってから30秒後になる。

旧設計の、再起動のあとに一時停止にしてホストの再開を待つ手順は、やめる。作り直しはデプロイや障害のたびに起き、そのたびにゲームが止まると遊べないためである。作り直しの間にも時計は進むが、作り直しは数秒で終わる見込みで（未検証）、影響は小さい。

### 2.8 rev の扱い

`rev` は、状態を変えるたびに1ずつ増やす通し番号で、取り消しでも戻さない（方式設計7.3）。

- コマンドを受け付けたら1増やす。
- 取り消しを行ったら1増やす。状態は前に戻っても、`rev` は進む。
- 参加者と席の変更（ロビー、席の再発行）も1増やす。
- 一時停止と再開も1増やす（3.3）。
- 接続の状態（`connected`）の変化では増やさない。誰かが再接続するたびに、全員の表示の照合（BD03 3.3）が古いと判定されることを避けるためである。

`rev` は `room` の表に保存し、増やすたびに、変更の中身と同じトランザクションで書く。ロビーの変更も保存するため、作り直しや休止をまたいでも `rev` は戻らない。旧設計の `bootId`（起動ごとの乱数で、`rev` の戻りを見分ける値）は要らなくなる。

### 2.9 取り消しの手順

取り消しは、管理操作の `undoLast(seq)` で行う。取り消せるのは、最後の有効な行1つだけである。さらに前の行を取り消したい場合は、繰り返す。

1. 管理を許された大画面には、取り消しの対象になる行（最後の有効な行）の `seq` と、人が読める説明（「Ben：日本語の支払い（単語、1コイン）」など）を送っておく（BD03 1.3 の `lastCommand`）。
2. ホストが「1つ取り消す」を押し、確認で実行を押すと、大画面は表示中の `seq` を付けて `undoLast` を送る。
3. Durable Object は、`seq` が最後の有効な行と一致するかを確かめる。違えば拒否する（`STALE_TARGET`）。確認の間に別のコマンドが入った場合に、ホストが見ていない行を取り消さないためである。最後の有効な行がゲームの作成の行なら、取り消すものがないとして拒否する（`NOTHING_TO_UNDO`）。最後の有効な行の `state` でゲームが終わっていれば拒否する（`GAME_OVER`）。
4. 対象の直前の有効な行の `state` を読み、取り消したあとの状態とする。
5. 取り消しの行（`undo` に対象の `seq`、`state` に手順4の状態）を追記し、`rev` を1増やす。
6. 全端末に `view` を送り、出来事 `undone`（取り消した行の説明を含む）で、取り消されたことを大画面とスマホに出す。

「有効な行」は、取り消しの行の `undo` に並んだ行と、取り消しの行そのものを除いた行である。取り消しを繰り返すと、有効な行の最後が1つずつ前に移る。

対象は、誰が送った行でもよい。手番でない人の日本語の支払いや、管理操作の `callLastRound` も、最後の行なら取り消せる。`callLastRound` より前の行を取り消す場合は、`callLastRound` が先に取り消される。必要なら、ホストがもう一度押す。

取り消しで状態が戻っても、出された問いや交換の申し出は、戻した状態に含まれるものだけになる。消えた申し出は、各スマホで表示から消える。

取り消しても、すでに見えた情報は消えない（方式設計8.2）。

ゲームを終わらせた行（目標点での勝ち、最終ラウンドの終わり、`abortGame`）を取り消せないのは、終局で全注文の条件を公開するためである（BD03 1.2）。取り消して再開すると、全員が残りの注文の条件を知ったまま続けることになる。`abortGame` の押し間違いは、確認の画面で防ぐ（BD04）。

### 2.10 エンジンの版の確認

コードをデプロイすると、すべての Durable Object が作り直され、新しいコードで動く。遊んでいる途中の部屋も同じである。

新しいエンジンが、古いエンジンの作った状態の写しを正しく読めるとは限らない。そこで、2.7の手順2で `meta` の `engineVersion` と今のコードの版を比べ、違えば部屋を止める。止めた部屋は、すべての接続に `error`（`ENGINE_CHANGED`）を返し、大画面に次を出す。

- 記録を作ったエンジンの版と、今のエンジンの版。
- 対処の手順：記録を作った版に戻してデプロイし直す。`wrangler rollback` で戻せるのは直近の100版までで、Durable Object のクラスを足したり消したりした版をまたいでは戻せない（Cloudflare の資料）。その場合は、該当のコミットを取り出してデプロイする。

違う版で続ける選択肢は作らない。写しの形や判定が変わっていると、誰も意図していない状態で続くためである。

比べるのはエンジンの版だけで、画面や Worker だけを直したデプロイでは部屋は止まらない（2.2）。それでもデプロイは全員の接続を一度切るため、遊ぶ予定の日の前に済ませておく（4.4）。

### 2.11 部屋の作成と削除

部屋は、大画面の起動画面（BD04 H01）で「部屋を開く」を押したときに作る。

1. 大画面は、ホストの鍵を付けて `POST /api/rooms` を送る。
2. Worker は部屋の ID を作り、その Durable Object に初期化を頼む。Durable Object は、ここで初めて表を作り、`room` の表に「ロビー」を書く。
3. Worker は部屋の ID を返す。大画面は、部屋の ID を `localStorage` に保存し、大画面のURL（`/board?room=<部屋の ID>`）に移る。

`hello` や HTTP の要求で、初期化されていない部屋の ID を指定された場合、Durable Object は `error`（`ROOM`）を返す。表を作るのは手順2の初期化のときだけで、コンストラクタでは表を作らない（2.7の手順1）。推測で作った部屋の ID で、保存が増えることを防ぐためである。初期化されていない Durable Object が保存の量に数えられるかは、資料に書かれていない（未検証）。

部屋の一覧は持たない。続きを開く部屋は、次のどれかで選ぶ。

- 大画面の `localStorage` に保存した部屋の ID（同じPCの同じブラウザ）
- 大画面のURL。ロビーの画面（BD04 H02）に出しておき、ホストがブックマークする
- 参加者のスマホのURL（`/p?room=<部屋の ID>`）に入っている部屋の ID

部屋の一覧を持つには、部屋とは別に一覧用の Durable Object を置き、作成と削除のたびに両方に書く必要がある。2つの書き込みは1つのトランザクションにならず、片方だけ失敗すると一覧と部屋が食い違う。数回の試遊では、上の3つで足りる。

部屋の削除（`DELETE /api/rooms/<roomId>`）は、記録を取り出したあとに、その部屋を開いている大画面からホストが行う。Durable Object は `ctx.storage.deleteAll()` で自分の保存をすべて消す。部屋は自動では消さない。削除の前に記録を取り出し損ねると、戻せないためである。

## 3. 時計

### 3.1 数える範囲

ゲームの経過時間は、準備の完了（BD01 6.2、最初の手番の開始）から数え、一時停止の間を除く。

### 3.2 時刻の取り方

経過は、`room` の表に持つ次の3つの値と、サーバーの今の時刻（`Date.now()`）から求める。

| 値 | 内容 |
|---|---|
| `startedAt` | 準備の完了の時刻 |
| `pausedTotalMs` | これまでの一時停止の合計 |
| `pausedSince` | 一時停止中なら、その始まりの時刻。進行中なら空 |

経過 ＝ 今の時刻 − `startedAt` − `pausedTotalMs` −（一時停止中なら 今の時刻 − `pausedSince`）

旧設計では、ホストPCのスリープで時計が飛ぶことに備え、単調時計と1秒ごとの見張りを使っていた。サーバーが Cloudflare に移ったため、ホストPCのスリープは時計に影響しない。Cloudflare のサーバーの時刻は同期されている前提とし、単調時計と見張りはやめる。

Workers の `Date.now()` は、1回の処理の中では進まない。経過は、メッセージを処理するたびにその時点で求めるため、この性質は影響しない。

Durable Object の作り直しや休止の間も、時計は進む。作り直しが数秒で終わる見込みで（2.7）、旧設計の「サーバーが止まっていた間は数えない」規則はやめる。

### 3.3 一時停止

一時停止は、時計とプレイヤーのコマンドの受け付けを止める、部屋（Durable Object）だけの状態である。エンジンのコマンドにはしない。

- ホストが大画面で一時停止を押すと（管理操作 `pause`）、`room` の表に `pausedSince` を書き、`rev` を1増やす。出来事 `paused` を全端末に送る。
- 再開（管理操作 `resume`）では、`pausedTotalMs` に足して `pausedSince` を空にし、`rev` を1増やす。出来事 `resumed` を送る。
- 一時停止の間は、プレイヤーのコマンドを `reject`（`PAUSED`）で拒否する（1.3の手順2）。管理操作は受け付ける。

一時停止をエンジンのコマンドにしないのは、取り消しを単純にするためである。エンジンの状態に一時停止を持たせると、取り消しで一時停止の前まで戻ったときに、時計とエンジンの状態が食い違う。それを避けるには、一時停止の行を取り消しの対象から外して再適用する特別な扱いが要る。

一時停止の時刻は、記録の `commands` には残らない。手番の時間（`elapsedMs`）は一時停止を除いた経過で書くため、集計には影響しない。

70分を過ぎても、サーバーは何もしない。打ち切りはホストの `callLastRound`（BD01 8.5）で行い、ほかの管理操作と同じく記録に残る（方式設計5.9）。MVP では Alarm を使わない。

大画面の経過の表示は、`view` の `clock`（BD03 1.4）から端末が数え進める。サーバーは1秒ごとに時刻を送らない。

## 4. デプロイと運用

### 4.1 前提

| 項目 | 内容 |
|---|---|
| Cloudflare | 開発者の個人のアカウント。Workers の無料プラン。開発者の別のアプリ（`beb-party`、`beb-raid-api`、`beb-raid-api-dev`）と同じアカウントに置く |
| Worker の名前 | `word-farm`。同じアカウントのほかの Worker と重ならない名前にする |
| 配信先 | `https://word-farm.r-sagishi.workers.dev`（アカウントのサブドメインは `r-sagishi`） |
| デプロイの道具 | `wrangler`（`app/packages/worker` の開発の依存に入れる） |
| デプロイする PC | Node.js が動く開発者の PC。会社の PC でもよい。デプロイは外向きの HTTPS の通信だけで行える |
| ホストPC | 会社の Windows 11 のノートPC。大画面ビューをブラウザで開くだけで、サーバーは動かさない |
| スマホ | 参加者の私物。各自のモバイル通信（4G/5G）でつなぐ。社内の Wi-Fi にはつながない |

### 4.2 費用をかけないための決まり

費用をかけないことを、この構成の条件とする。次を守る。

- Workers の有料プラン（Workers Paid）に上げない。
- 支払いの手段を登録しない。アカウントは作成済みで、無料プランのまま別のアプリをデプロイできている。アカウントの持ち主は支払いの手段を登録していない。有料プランへの切り替えには支払いの手段が要るため、無料プランのままである（管理画面の表示は見ていない）。
- 有料プランでだけ使える機能を使わない。使う機能は、Workers、Workers Static Assets、SQLite の Durable Objects に限る。
- 設定ファイル（`wrangler.jsonc`）で、Durable Objects に SQLite の保存（`new_sqlite_classes`）を指定する。無料プランでは SQLite の Durable Objects だけが使える。
- カスタムドメインを取らない。`workers.dev` のサブドメインを使う。

無料プランの上限は次のとおりである（Cloudflare の料金の資料、2026-10-27 に確かめた）。上限を超えると、その種類の処理がエラーになり、上限は毎日 UTC の0時（日本時間の9時）に戻る。課金はされない。

| 上限（1日） | 値 | 1局の見積もり（未検証） |
|---|---|---|
| Workers の要求 | 100,000 | 数百（画面の読み込み、API、WebSocket の接続） |
| Durable Objects の要求 | 100,000 | 約300。受けた WebSocket のメッセージは20件で1要求と数える。コマンド約1000件と、端末の生存確認の約2700件（BD03 3.7）で約190、接続が数十 |
| Durable Objects の時間 | 13,000 GB-s | 最大で約700（128MB × 90分。休止の間は数えない） |
| SQLite の行の読み込み | 5,000,000 | 数千 |
| SQLite の行の書き込み | 100,000 | 約3000。コマンド1件で、`commands` の1行、`id` の索引、`room` の更新の約3行と数える（索引の更新も1行と数える。Cloudflare の資料） |
| 保存の容量（合計） | 5GB | 1局で数MB〜数十MB（6章） |

上限はアカウントの単位で数えるため、同じアカウントの別のアプリと分け合う。2026-09-27〜10-27 の別のアプリの使用量は、1日の最大で Workers の要求が390、Durable Objects の要求が295だった（Cloudflare の分析のデータ）。分け合っても上限には遠い。

どの上限も、1日に数局を遊ぶ使い方では届かない見込みである。上限に届くとゲームが止まるため、使用量は M5 の実機のテストと試遊の後に、Cloudflare の管理画面で確かめる。

### 4.3 初回の準備

1. 既存の Cloudflare のアカウント（4.1）を、無料プランのまま使う（4.2）。
2. 開発者の PC で `npx wrangler login` を実行し、ブラウザで認証する。認証は期限が切れるため、デプロイの前に `npx wrangler whoami` で確かめる。
3. ホストの鍵を作り、`npx wrangler secret put HOST_KEY` で設定する。鍵はパスワードの管理の道具などに控え、ホストに渡す。
4. `app/` で `npm ci` と `npm run build` を実行し、`npm run deploy`（中で `wrangler deploy` を呼ぶ）でデプロイする。
5. ホストPCのブラウザで大画面のURL（`https://…/board`）を開き、ホストの鍵を入れる。
6. ホストPCの電源の設定を確かめる。旧設計と違い、ホストPCがスリープしてもサーバーは止まらない。ただし大画面が消えるため、遊ぶ間は電源につなぎ、スリープまでの時間を長くしておく。

大画面ビューは、画面の消灯を防ぐ機能（Screen Wake Lock）を取る。HTTPS のページでは使える。会社のPCで、無操作のときの画面のロックがグループポリシーで強制されている場合に、これで止められるかは確かめていない（未検証）。止められない場合は、遊ぶ間はホストが時々PCを操作する運用にする。

### 4.4 デプロイの決まり

デプロイすると、遊んでいる途中の部屋も含め、すべての Durable Object が作り直され、全員の接続が一度切れる（Cloudflare の資料）。版が変わった部屋は止まる（2.10）。

- 遊ぶ予定の日の前日までにデプロイを済ませる。遊んでいる間はデプロイしない。
- デプロイの前に、エンジン、サーバー、E2E のテストを通す（BD06）。
- デプロイした版（git のコミット）を控える。遊んだあとに直したコードをデプロイすると、続きを遊ぶ部屋が止まる。続きを遊ぶ部屋がある間は、直したコードをデプロイしない。

### 4.5 遊ぶ日の手順

1. ホストPCのブラウザで大画面のURLを開く。保存したホストの鍵で管理ができることを確かめる。
2. 「部屋を開く」を押す（2.11）。
3. ブラウザを全画面にし、HDMI でテレビかプロジェクターに映す。
4. 参加者が自分のモバイル通信のまま、QRコードを読み、名前（あだ名）を入れて参加する。
5. ホストが大画面で参加者を時計回りに並べ、上級者の倍率（BD01 8.4）を設定して、ゲームを始める。

旧設計の、ホットスポットの有効化、ファイアウォールの許可、QRコードに入れるアドレスの選択は要らない。

### 4.6 QRコード

| 用途 | 入れるURL |
|---|---|
| 参加 | `https://<配信先>/p?room=<部屋の ID>` |
| 席の作り直し（方式設計7.4の手順4） | `https://<配信先>/p?room=<部屋の ID>&claim=<使い捨ての合言葉>` |

使い捨ての合言葉は、ホストが席の作り直しを押すたびに作り、1回使われるか5分たつと無効にする。

席の作り直しのQRコードは、大画面に出す。合言葉で入った端末には、どの席かを確かめさせ、ホストが大画面で承認してから、その席の新しいトークンを発行し、古いトークンを無効にする（BD03 3.6）。テレビに映ったQRコードを別の参加者が先に読んでも、ホストが承認しなければ席は移らない。全員が同じ部屋にいるため、ホストは誰の端末かを目と口で確かめられる。

QRコードをホストPCの画面の小窓に出し、大画面に出さない案は採らない。ホストPCの画面を複製の表示でテレビに映すと、小窓もテレビに映るためである。

QRコードの画像は、大画面のブラウザでライブラリ（例：`qrcode`）を使って作る。部屋の ID を外部のサービスに送らないためである。

### 4.7 終わり方と後片付け

1. ゲームが終わったら、ホストは大画面の「記録を保存」を押す（5.1）。ホストPCのダウンロードのフォルダに、記録のファイルが保存される。
2. 保存したファイルを開けることを確かめてから、大画面で部屋を削除する（2.11）。続きを遊ぶ場合は削除しない。
3. 記録のうち、名前を伏せたもの（5.3）だけをリポジトリの `sim/results/` などに移す。

### 4.8 障害の時の対処

| 事象 | まず確かめること | 対処 |
|---|---|---|
| スマホがつながらない | スマホがモバイル通信につながっているか。電波が届いているか | 電波の届く場所に移る。モバイル通信を使えないスマホは、別の人の端末を借りる |
| 大画面が開けない | 会社のネットワークで `workers.dev` が開けるか | ほかの端末（私物のノートPC、タブレット）で大画面を開き、HDMI で映す |
| 全員の接続が一度に切れた | 大画面の表示 | 自動で再接続するのを待つ。Durable Object の作り直しで起きる（2.5）。戻らない場合は大画面を読み込み直す |
| 大画面に「エンジンの版が違います」と出る | 遊んでいる間にデプロイしていないか | 記録を作った版に戻してデプロイし直す（2.10）。戻せない場合は、紙で続きを遊ぶ |
| 大画面に「サーバーの上限に達した可能性があります」と出る、ページで Error 1027 が出る | Cloudflare の管理画面の使用量。Error 1027 は Workers の上限で、Durable Object の上限は番号のない失敗になる（2.5） | 無料の上限は日本時間の9時に戻る。その日は紙で遊ぶ（4.2） |
| Cloudflare が止まっている | Cloudflare の稼働状況のページ | 紙で遊ぶ。紙の道具は毎回持っていく（方式設計14.1） |
| スマホをなくした、電池が切れた | ほかの端末を用意できるか | 管理操作で席を作り直し、席専用のQRコードを別の端末で読む（4.6） |
| 大画面のブラウザでホストの鍵が消えた | ブラウザの閲覧データを消していないか | 鍵を入れ直し、ブックマークした大画面のURLか、参加者のスマホのURLから部屋を開き直す（2.11） |
| 大画面がロック画面になった、PCがスリープした | 電源の設定（4.3の手順6） | ロックを解除し、大画面を開き直す。サーバーは止まっていないため、ゲームはそのまま続く。一時停止が要る場合はホストが押す |

試作は、WebSocket の往復と SQLite への書き込みをする Durable Object 1つで作り、無料プランのアカウントにデプロイする。

| スマホのモバイル通信でつながるか | iPhone と Android で、QRコードからページを開く | 4.5 | 済み。別のアプリ（`beb-party`）を、社内で各自のモバイル通信で複数回遊べている |

## 5. 記録の書き出し

### 5.1 取り出しと書き出し

記録の書き出しは、ゲームが終わったあと（出来事 `gameOver` か、管理操作 `abortGame` のあと）にだけ行える。ゲームの途中に記録を取り出すと、`seed` と伏せた注文が見えてしまうためである（2.2）。

1. ホストが大画面で「記録を保存」を押す。
2. 大画面は、ホストの鍵を付けて `GET /api/rooms/<roomId>/record` を送る。Durable Object は、`meta`、`participants`（トークンのハッシュを除く）、`commands`（`state` の列を除く）を JSON で返す。
3. 大画面のブラウザは、エンジンで記録の有効な行を先頭から再適用し、出来事を作る。取り消された行の出来事は、再適用しないため含まれない。
4. 大画面は、5.2 のファイルを作り、1つの zip にまとめてダウンロードさせる。

再適用をブラウザで行うのは、Durable Object の1件の処理を短く保つためである（1.4）。エンジンは入出力のない純粋な関数で、ブラウザでもそのまま動く（方式設計4章）。

手順2で `state` の列を除くのは、取り出す量を減らすためである。写しは手順3の再適用で作り直せる。

| ファイル | 内容 |
|---|---|
| `record.json` | 取り出した記録そのもの（手順2の応答）。5.4 の検証と、あとからの集計のやり直しに使う |
| `summary.json` | 1局の概要（5.2の末尾） |
| `turns.csv` | 手番ごとの1行 |
| `points.csv` | 点を得た出来事ごとの1行 |
| `actions.csv` | 行動、銀行、交換、日本語の支払いの出来事ごとの1行 |
| `orders.csv` | 注文と共同注文ごとの1行 |
| `farms.csv` | 手番の終わりごとに、各人の作物、動物、産物の数を1行ずつ |

`summary.json` と CSV は、名前を入れた組（`summary_named.json`、`*_named.csv`）と、名前を伏せた組の2組を作る（5.3）。

### 5.3 名前の扱い

参加者の名前は、社内の人の名前であることが多い。外部のサービスとリポジトリに、本名を残さないようにする。

- 参加画面で、あだ名で入るよう促す（2.6）。
- 書き出しには、名前を入れたもの（`*_named.csv`、`summary_named.json`）と、名前を `P0`〜`P3`（席の番号）に置き換えたもの（`*.csv`、`summary.json`）の2組を入れる。
- リポジトリに移してよいのは、名前を置き換えた組だけとする（4.7の手順3）。`record.json` は名前を含むため、リポジトリに移さない。
- `commands` には名前を書かず、席の番号だけを書く。名前は `participants` だけに置く。
- エンジンの状態（`GameState`）にも名前を持たせない（2.6）。ゲームの作成（`createGame`）の行にも、名前ではなく `participantId` を書く。状態の写し（2.4）にも名前は入らない。
- 部屋を削除すると（2.11）、Cloudflare の保存から名前も消える。

### 5.4 記録の検証

開発の道具 `app/packages/protocol/tools/verify.ts`（`npm run verify -w @word-farm/protocol -- <record.json>`）は、`record.json` と、Durable Object から取り出した状態の写しを読み、記録を先頭から再適用して、各行の写しと比べる。旧設計で起動のたびに行っていた照合を、開発者が必要なときに行う形に移したものである。

写しを含めて取り出すには、ホストの鍵を付けて `GET /api/rooms/<roomId>/record?states=1` を送る。ゲームが終わった部屋に限る。

使うのは次の場合である。

- エンジンを直したあとに、過去の記録で判定が変わらないかを確かめる。
- 試遊のあとで、記録と状態の食い違いが疑われるときに調べる。

### 6.1 試験用の口

Worker の設定に `TEST_HOOKS=1` があるときだけ、`/api/rooms/<roomId>/test/` の下に次の口を開く。`wrangler.jsonc` には書かず、Miniflare の結合テストと、手元の `wrangler dev`（`app/packages/worker/.dev.vars`。git の対象外）でだけ渡す。デプロイした版では、これらの口は404を返す（BD06 TC-SRV-17）。

| 口 | 内容 | 使うテスト |
|---|---|---|
| `state` | 今の状態とメモリ上の値を読む | 結合テスト、E2E |
| `crashNext` | 次の書き込みの確定の直後に作り直させる（障害注入） | TC-SRV-03、20 |
| `version` | エンジンの版を差し替える | TC-SRV-04c、21 |
| `restart` | 作り直させる | TC-SRV-04c、E2E-13 |
| `tables` | SQLite の表の一覧 | TC-SRV-08c |
| `give` | 席にカード、産物、コインを渡す。カードは山から渡し、総数を保つ。最後の行の写しを書き換えるため、記録の検証では食い違いになる | E2E（注文、共同注文、交換など） |
| `advance` | 準備を最後まで、または n 手番を、エンジンのコマンドを通常どおり適用して進める | E2E の前置き |

### 6.2 動作の記録

Durable Object と Worker は、起動、接続と切断、拒否、保存の異常、版の不一致を、`console.log` に1行1件で出す。手札の中身や注文の条件など、秘密の情報と、ホストの鍵とトークンは書かない。

見るときは、開発者の PC で `npx wrangler tail` を動かす。無料プランで記録を残す機能（Workers Logs）の上限と保存の期間は確かめていない（未検証）。MVP では、遊ぶ間に必要なら `wrangler tail` で見る運用とし、記録を残す機能に頼らない。

1つの `view` の送信のような頻繁な処理は書かない。
